# Decisions


Choices made while building M0 and M1, and places where the design was unclear or did not match what the machines do. Each entry says what the design or brief said, what was found, and what was done.

## Environment findings

**E1. Claude Code on Mantis runs as root, and root cannot use bypass mode.**
`ssh mantis '/root/.local/bin/claude -p "say ok" --dangerously-skip-permissions'` prints `--dangerously-skip-permissions cannot be used with root/sudo privileges for security reasons` and exits 1. Root is the only user on Mantis. No user was created on the shared VPS. Test agents on both machines get the same scoped allowlist instead (`test/e2e/agent.sh`): `defaultMode: dontAsk` plus file tools and a few read-only commands in the test project's `.claude/settings.json`, and the adapter's own allow rule for `handloom`. In `dontAsk` mode a tool call outside the list is denied with an error the agent reads; it never opens an approval prompt. The first rehearsal used `acceptEdits` and showed why this matters: the lead tried `find` to double-check a file, stopped at an approval prompt, the adapter reported `blocked`, and the job hung until the timeout.

**E1b. Claude Code shows a "trust this folder" dialog in a new directory.** When the folder pre-approves permissions, the dialog's default answer is "No, exit". `test/e2e/m1.sh` answers it (Down, Enter) during setup, before the brief, and counts those keys in its output. Without trust, Claude Code ignores the project's allow rules.

**E2. Claude Code on Mantis was not logged in.**
`claude auth status` on Mantis returned `"loggedIn": false`. Credentials were not copied from GB10. The owner logged in later the same day and M1 then ran. `test/e2e/m1.sh` checks the login first and stops with a clear message.

**E3. Two Claude Code versions on Mantis.**
A non-interactive shell finds `/usr/local/bin/claude` (2.1.202). The newer one is `/root/.local/bin/claude` (2.1.220). GB10 has 2.1.288. The e2e script uses `/root/.local/bin/claude` by absolute path (`REMOTE_CLAUDE`). After the login that one had updated itself to 2.1.288, so the M1 runs used 2.1.288 on both machines.

**E4. Different CPU architectures.**
GB10 is arm64, Mantis is amd64. Go 1.27.1 is installed in `~/.local/go` on GB10 (checksum verified against go.dev). The Mantis binary is cross-compiled with `CGO_ENABLED=0 GOOS=linux GOARCH=amd64`; the pure-Go SQLite driver makes that work.

**E5. Herdr's Claude hook reports the session, not the state.**
`~/.claude/hooks/herdr-agent-state.sh` handles `SessionStart` only and sends the session id to Herdr's socket. It does not report idle, working or blocked. So handloom cannot learn Claude Code's state from that hook and installs its own. No Herdr code was copied, so its licence was not a question. handloom never edits `~/.claude/settings.json`; its hooks go in the project.

**E6. `dontAsk` mode denies shell redirects to files.** Tested with the test allowlist: `uname -r && hostname` and `uname -r | cat` are allowed, `uname -r > k.txt` is denied even with `Write` allowed. In the second two-machine M1 run the worker hit this, stopped and asked "the user". The allowlist was not widened: allowing all of Bash for an unattended root agent would defeat the reason Claude Code refuses bypass mode as root. Instead the adapter's instructions now say that nobody is watching, that a denied command should be retried another permitted way, and that a stuck agent blocks the task and messages the lead.

## Findings from the M1 runs

**F1. A stuck agent that has claimed nothing is invisible.** Leases cover claimed tasks. In the failed run the worker ended its turn without claiming its assigned tasks, and the lead waited with no notice. A fix for M2: the hub tells the lead when an assigned task is still unclaimed some minutes after its notice was delivered.

**F2. Agents may decline mail that looks unrelated.** In the hook check the worker read a message from a human asking it to send a reply and declined: the text arrived in a tool result and had nothing to do with its current request. That is the cautious behaviour principle 6 wants for agent messages, but it also applied to a `human:` sender. handloom's notices about tasks were acted on in every run, because the instructions block says to. If humans are to direct agents through handloom, the instructions need to say how much weight a `human:` message carries (M3, with the human channel).

**F3. The nudge rate limit shapes the pace.** One nudge per agent per 60 seconds means a second wake inside a minute waits. The three-task job took about 90 seconds, most of it that wait.

## Claude Code facts, verified

Checked against the installed CLI (2.1.288 on GB10) with a logging hook, and against the hooks reference.

- Hooks run with the agent's environment (`HANDLOOM_AGENT`, `TMUX_PANE` reach the hook). They also receive `cwd` and `session_id` on stdin.
- A `Stop` hook that prints `{"decision":"block","reason":"..."}` makes Claude continue with the reason as its next instruction. Tested: Claude answered the reason's request, then stopped. The second `Stop` input has `stop_hook_active: true`.
- Hooks in `.claude/settings.local.json` of the project run in `-p` mode and interactive mode.
- `SessionStart` output on stdout is added to the agent's context.
- `PermissionRequest` exists as a hook event and is the prompt way to see "blocked". `Notification` with `permission_prompt` also fires, later.
- Not tested here: `claude -p --resume <id>` (headless resume is M2).

## Design gaps and choices

**D1. Transport is plain HTTP on the Tailscale network.** The design says HTTPS. Section 13 allows a private network by default and makes TLS the public-exposure setup. The hub in the tests listens on the Tailscale address only. TLS is left for M4.

**D2. New agents register as `worker`.** The design says roles are set by a human or the admin, not by agents, but does not say what role a new agent has. A register request cannot carry a role (unknown fields are rejected with 400). `lead` and `observer` are given with `handloom agent role`, which only the admin or a human may call.

**D3. The admin token is for administration only.** The scope table has no admin column. The admin may read, and may create devices, humans and projects, set roles and read the audit log. It may not create tasks or send messages; a human token does that.

**D4. `assign` and `block` are separate API calls.** Section 12 lists no `assign` endpoint though the scope table has the action. Added `POST /tasks/{id}/assign`. `block` falls under the "own task" row.

**D5. Escalations: the scope check is live, the feature is not.** `POST /escalations` and `/escalations/{id}/answer` check the scope table and then return 501. A forbidden caller gets 403 today, so the rule "only a human answers" is enforced and tested before M3 builds the feature. The design marks "open escalation" as n/a for humans; the hub rejects it.

**D6. Events carry a target agent.** The design's `event` table has no column that says which device should receive an event. Added `agent_id`. The long-poll returns events whose target agent lives on the calling device.

**D7. The link is level-triggered.** Events only tell the link to look. It then asks the hub for its agents' state and mail counters (`GET /device/agents`) and runs the ladder from that. A lost or repeated event cannot lose or repeat a wake. The link also looks every 10 seconds, which drives the timers.

**D8. Hub notices are messages from `hub`.** Assignment, submit, accept, reject, cancel, release, block, lease expiry and "task can be claimed now" are sent as messages with sender `hub`. This makes "unread mail" the single trigger for the ladder and covers "a newly assigned task". The sender is always set by the hub from the credentials; a request that contains a `from` field is rejected.

**D9. Wake reports go through `POST /agents/{name}/wake`.** The audit log must show every wake, and wakes happen on the link. The link reports each typed nudge (`method: tmux|herdr`) and each failure (`method: none` with a reason). The end-of-turn hook calls `POST /agents/{name}/turn-end`, where the hub decides in one transaction whether to hold the agent (and logs `wake` with `method: hook`) or mark it idle. `POST /messages/{id}/delivered` from the design is also there.

**D10. "Once per batch" for the end-of-turn hook is tracked on the hub.** The agent row keeps the newest message id the hook has handed over. The hook holds the stop only for unread mail newer than that. This does not rely on Claude Code's `stop_hook_active`.

**D11. Re-nudge and "unknown".** The design says: two nudges with no `handloom inbox` call within 10 minutes mark the agent unknown. It does not say when the second nudge is sent if no new mail arrives. Choice: if delivered mail stays unread for 5 minutes, nudge once more. After two nudges and 10 minutes with no inbox call, report unknown. The link sees inbox calls because they pass through its socket.

**D12. A wake failure is reported once per episode.** The first M0 run reported "cannot be woken" to the lead for every new message to a plain shell. Now the link reports a given reason once and again only after the agent's state has changed. Known quirk: an agent with no adapter (a plain shell) never reports a state, so the lead still gets one "cannot be woken (state_unknown)" notice for it. It is true, but a lead that is an LLM may read it as a problem. M2 could skip the notice for agents that have never reported a state.

**D13. The nudge has no backticks.** The typed line is `You have N new handloom messages. Run: handloom inbox`. The design's example has backticks, which a shell would execute if the pane had fallen back to a shell. The tmux driver also refuses to type when the pane's foreground program is a shell.

**D14. tmux wins over herdr when detecting the wake target.** `$TMUX_PANE` is set by tmux for exactly that pane. `$HERDR_PANE_ID` can be inherited from an outer terminal: in the first M0 run a shell started from a Herdr pane recorded that pane as its wake target. Plain `--kind shell` agents now record no wake target at all.

**D15. Lease heartbeats come from activity, not from the state.** The design says adapters heartbeat while the agent is `working`. A hung agent would stay `working` and keep its lease for ever. The Claude adapter reports each finished tool call (`PostToolUse`), and the link extends the agent's leases at most every 2 minutes while such reports arrive.

**D16. Agent identity on a device.** The CLI names its agent with `$HANDLOOM_AGENT`, or a `.handloom/agent` file in the working directory or a parent. The hub checks that the named agent belongs to the calling device. Any process on a device can therefore act as any agent of that device: the device is the trust boundary. The socket is mode 0600.

**D17. Claude hooks go in `.claude/settings.local.json`.** The hook command is an absolute path to the binary, which is per-machine, and this file is the per-machine one. The adapter also adds an allow rule for `handloom` commands (`--no-permissions` skips it); without it every `handloom` call would stop at an approval prompt.

**D18. `adapter.yaml` is a description, not yet a driver.** The Claude adapter's installer is Go code. The manifest is embedded and documents the adapter. A generic manifest-driven installer belongs to M2, when there is a second adapter to shape it.

**D19. Device-offline detection is left out.** Agents become `offline` from the `SessionEnd` hook. The hub does not yet mark agents offline when their link disappears. M3's lead-silence alert needs it.

**D20. One hub holds several projects; the CLI defaults to `default`.** (Open question 2.) Agent names are unique per hub, so an agent's project is known from its name.

**D21. Module path is `handloom`.**

## Dependencies

- `modernc.org/sqlite`: pure-Go SQLite, as the brief asks, so the binary is static and cross-compiles without a C toolchain. It brings its own support modules (`modernc.org/libc`, `mathutil`, `memory` and a few small ones). Nothing else is imported outside the standard library.

# M2 decisions

## Environment findings (M2)

**E7. Codex on GB10 is logged out.** `codex exec` there fails with "Your access token could not be refreshed. Please log out and sign in again" (codex-cli 0.144.5, only in `~/.nvm/versions/node/v20.20.2/bin`). Codex on Mantis (0.160.0) works. The Codex worker runs on Mantis.

**E8. Pi has no working cloud model on either machine.** GB10: `pi auth check --provider openai-codex` returns `invalid`; the default model is the local Qwen. Mantis: Pi's OpenRouter key answers `403 Key limit exceeded`. So the only model Pi can use is the local Qwen. The owner's rule for the local model (work goes to it through OMP in a detached tmux run, one at a time, no input typed into a running session) does not fit a handloom worker that is woken by typed nudges, so I asked. The owner chose the local Qwen for this test. The Pi worker ran as one session with `--thinking low` (`PI_MODEL=local-qwen/qwen3.8-27b test/e2e/m2.sh`). It did the job; once it sent the same reply twice.

**E10. Claude Code's login on Mantis expired overnight** ("OAuth session expired and could not be refreshed"). `m2.sh` now checks that the headless worker's Claude Code can run a turn, and `HEADLESS_HOST=local` puts that worker on this machine.

**E9. OMP exists only on GB10 and uses the local Qwen. OpenCode on Mantis has no credentials** (a free model did not answer within 60 seconds). Neither adapter ran against a model.

## Codex facts, verified on Mantis (codex-cli 0.160.0, as root)

- Hooks have the same shape as Claude Code's: `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PermissionRequest`, `Stop`, `SessionEnd`; JSON on stdin with `session_id`, `cwd`, `hook_event_name`, `stop_hook_active`; the hook inherits the environment.
- A `Stop` hook that prints `{"decision":"block","reason":"..."}` makes Codex continue with the reason (tested: it answered the reason's request, then stopped).
- A project's `.codex/hooks.json` is loaded, with or without a git repository. Codex runs a hook only after the user has reviewed it: the TUI shows a "Hooks need review" dialog once and stores a hash in `~/.codex/config.toml`. `codex exec` has no dialog; there, and for unattended agents, `--dangerously-bypass-hook-trust` runs the hooks without the stored review.
- The same hooks given both in the project file and inline (`-c hooks.Stop=...`) fire twice. Register them in one place only.
- **In the TUI, `SessionStart` fires at the first prompt, not at launch.** Until then handloom would not know the agent exists.
- Hooks run outside the sandbox. The agent's shell commands run inside it. In `workspace-write` the sandbox blocks unix sockets, inside or outside the workspace, and `--add-dir` does not help; only `sandbox_workspace_write.network_access=true` opens them. Writes outside the workspace are refused, also as root.
- MCP servers run outside the sandbox. With approval policy `never`, an MCP tool call fails ("requires approval, but approval policy is never") unless the server has `default_tools_approval_mode = "approve"`.
- Codex adds a `[projects."<dir>"]` trust entry to `~/.codex/config.toml` for a directory it runs in. The probe entries were removed by hand; the e2e run leaves one entry for `/root/hltest/codex-project`.

## Design choices (M2)

**D22. One hook handler for every kind.** `handloom hook <kind>` reads the Claude-shaped hook JSON. Claude Code and Codex call it directly. Pi, OMP and OpenCode get a small shim (extension or plugin) that turns their own events into the same JSON and calls the same command. For the end-of-turn delivery the shim reads the handler's `decision: block` answer and gives the reason to the agent as a user message.

**D23. Codex uses handloom through MCP, with the sandbox left on.** The alternative, turning on network access in the sandbox so the `handloom` command can reach the link's socket, gives the agent's shell the whole network. The MCP server runs outside the sandbox and offers only the handloom verbs. The tools are pre-approved (`default_tools_approval_mode = "approve"`) because nobody is there to approve them; scopes are still enforced by the hub. Nothing is written to `~/.codex/config.toml` by handloom: the MCP server is given on the command line.

**D24. `handloom run <name> -- <command>`.** Because Codex's `SessionStart` comes late, the agent is started through `handloom run`, which records the terminal and directory, reports the agent idle and then becomes the command. It works for any kind.

**D25. `--dangerously-bypass-hook-trust` in the e2e script.** This skips Codex's review of hooks; it is not the approvals-and-sandbox bypass. The script uses it because the hooks were written a moment earlier by `handloom adapter install` and because the review would otherwise be stored in the owner's Codex config on every run. A person starting Codex by hand answers the review dialog once instead.

**D26. Headless resume is opt-in.** An agent is woken by a headless turn only if its wake target is `headless`: set by `handloom register --wake-target headless`, or by the hooks when the agent runs with `HANDLOOM_HEADLESS=1` (the link sets this for the turns it starts). An interactive agent that has gone offline is not resumed behind its owner's back; the lead is told instead. The design's wording ("no live terminal but a session id") would also cover that case; it can be widened later.

**D27. Headless commands are a table with overrides.** Defaults per kind are in `internal/link/headless.go`; `$HANDLOOM_HOME/headless.json` replaces one, for an absolute path or extra flags. Only the Claude Code line ran against the real CLI. A headless agent's project is not "trusted" by Claude Code, which then ignores the project's allow rules, so the e2e passes the allowlist on the command line through this file.

**D28. The agent's working directory is stored.** A headless turn must run in the agent's project. `register` and the session-start hook send `dir`.

**D29. MCP server written by hand.** About 300 lines: `initialize`, `ping`, `tools/list`, `tools/call` over newline-delimited JSON-RPC. No new dependency. Each tool call runs the same code as the command line, so scopes, errors and the audit log are identical. A failed command is a tool result with `isError`, so the agent can read the reason.

**D30. A blocked agent is reported after 30 seconds, not at once.** With approval policy `never`, Codex fires `PermissionRequest` and then denies the call itself; the agent is "blocked" for a moment. Reporting that to the lead was noise.

**D31. Unclaimed assigned tasks are reported** (finding F1). If an assigned task that could be claimed stays unclaimed for 10 minutes (`handloom hub serve --unclaimed`), the hub tells the lead once and logs `task.unclaimed`.

**D32. Adapter files.** Codex: `.codex/hooks.json`. Pi: `.pi/extensions/handloom.ts` (needs `pi --approve`). OMP: `.handloom/omp-extension.ts`, loaded with `omp -e`. OpenCode: `.opencode/plugins/handloom.js`. All put the protocol block in `AGENTS.md`. handloom never writes to `~/.codex`, `~/.pi`, `~/.omp` or `~/.config/opencode`.

## Setup script

**D33. `handloom link install` and `handloom hub install` write systemd units; `scripts/setup.sh` drives them over ssh.** The design names `handloom link install` (section 14). Root gets a system unit, anyone else a user unit (with lingering, so it survives logout). The unit copies the installing shell's PATH, because the link starts agent CLIs for headless turns. The script builds on the machine it runs from and cross-compiles for the server, so the server needs nothing installed. Linux and systemd only; launchd, prebuilt releases and a Docker image stay in M4. Tested on GB10 (user service) and Mantis (system service): hub, two devices, a message between them, rerun, status, remove. The test install was removed afterwards.

## Milestone A (Handloom workspace, see docs/WORKSPACE-DESIGN-v0.4.md)

**D34. `handloom ask` does not block by default.** DESIGN.md section 11 says `handloom ask` blocks until answered or `--timeout`. A blocked agent holds a turn open (and a tool call that may time out) for as long as the human takes. Instead `handloom ask` opens the escalation and returns at once; the answer arrives as a message from `human:<name>` and the normal wake ladder wakes the lead. `--wait <duration>` polls `GET /v1/escalations/{id}` client-side for scripts and tests; the server never holds a request or transaction open for the wait.

**D35. Escalation scopes and shape.** Only the lead opens (`escalation.open`), only a human answers (`escalation.answer`; the admin token may not). Everyone with read access may fetch one escalation by id, which is how `--wait` polls. The answer must be one of the options when options were given, free text otherwise, and only once (409 after that). The asker receives the answer as an ordinary message whose sender is taken from the answering credentials, so an agent cannot forge `human:`. Open and answer are audited and emit events.

**D36. Notifications carry a link, never content.** A new escalation sends one generic line ("The lead has a question for you") and a link to the inbox through ntfy and/or a generic webhook. The question and the answer stay on the hub; a push service is a third party. Settings come from the environment, so secrets stay out of argv and service files' command lines: `HANDLOOM_BASE_URL`, `HANDLOOM_NTFY_URL`, `HANDLOOM_NTFY_TOPIC`, `HANDLOOM_NTFY_TOKEN`, `HANDLOOM_WEBHOOK_URL`. Sending runs after the request commits, in the background with a 15 s limit; a failure is logged, never returned to the lead, because the escalation is stored and shows in the inbox either way. Web push is deferred (needs a service worker and HTTPS; fragile on iOS).

**D37. The store boundary is scoped down.** v0.3 promised that SQLite-specific SQL would live in one package. The hub has about 55 raw SQL call sites (agents, tasks, messages, escalations), so a full move behind a store interface is a multi-day refactor that delivers nothing visible. Decision: all NEW persistence for the web UI (accounts, sessions, settings, tokens) goes through methods in `internal/store`, written dialect-neutral where cheap; the existing hub SQL stays. The Postgres migration path is therefore "possible but not prepared"; docs must not promise it. Revisit when there is a concrete reason to leave SQLite.

**D38. Container.** Multi-stage build; the builder runs on the build platform and cross-compiles (`GOARCH=$TARGETARCH`), so an arm64 box builds the amd64 image the VPS needs without emulation. The runtime is distroless static, non-root (65532), with `/data` created and owned in the build stage so a fresh named volume is writable. No shell in the image, so `HEALTHCHECK` is `handloom healthcheck`. `hub serve --auto-init` creates the database on first start and logs the admin token once; the setup-code flow in C4 replaces that for the web. Backups use `VACUUM INTO` (safe while running); `hub restore` checks integrity and schema version, refuses to overwrite without `--force`, and clears stale `-wal`/`-shm` files. Before a migration changes an existing database the hub writes `backups/pre-vN.db`; a database with a newer schema than the binary is refused. Verified on GB10: build, health, backup/restore round trip, restart persistence, and an amd64 cross-build. Not verified: Dokploy.

**D39. Web accounts and sessions.** Humans gain `password_hash` and `role` (owner, member, viewer; API-only humans are members). Passwords: argon2id (64 MiB, 3 passes, 2 threads), at most 2 hashes at once, a dummy hash for unknown names so timing does not reveal them, at least 12 characters. Sessions: random 256-bit id in the cookie, only its SHA-256 in the database, a new id at every login, idle timeout 12 h and absolute 7 days (checked on every request, configurable), purged at login. Cookie `__Host-handloom_session` (Secure, HttpOnly, SameSite=Lax, Path=/) over https; plain `handloom_session` on localhost or with `HANDLOOM_INSECURE=1`. Lax rather than Strict so a link from a phone notification opens signed in; state changes are POST-only and need the session's CSRF token (form field or `X-CSRF-Token`) plus a matching Origin. Login and setup have no session yet, so they require a same-origin Origin or `Sec-Fetch-Site`. Login is rate limited per address and per name before any lookup or hashing. Behind a proxy `HANDLOOM_TRUST_PROXY=1` uses the last `X-Forwarded-For` entry (the one our proxy appended); otherwise the socket address.

**D40. First-run setup.** The owner does not exist until someone presents a one-time setup code printed in the hub's log at start (stored only as a hash). The wizard is open exactly while no human has `role=owner` with a password, so an upgraded hub whose humans only have API tokens still gets a wizard, behind the code. Creation runs in one transaction that re-checks "no owner", so simultaneous submissions create one. A restart with an owner deletes the stored code. There is no web password reset and no email: `handloom hub reset-password <name>` (needs the database) prints a new password once and signs that human out everywhere.

**D41. The web UI is off unless it can be safe.** It needs `HANDLOOM_BASE_URL` set to https, to localhost, or `HANDLOOM_INSECURE=1`. Otherwise every web route answers 503 with the reason (and the log says so); the API is unaffected. This keeps existing Tailscale-over-http hubs working without silently serving a login form over plain http. `HANDLOOM_SECRET` (v0.4) is not introduced yet: nothing needs a signing key, because sessions and CSRF tokens are random values stored server-side. Add it when something needs one.

**D42. Viewer.** A viewer (`role=viewer`) may read and nothing else, through the API as well as the web UI (`human:viewer` in the scope table).

**D43. One digest, plain pages.** `GET /v1/digest` is the single source for the inbox, and for the TUI and phone later: needs-you (open escalations, blocked tasks, a lead offline or unknown for over 30 minutes while work is open), to-review (submitted tasks), running, agents, recent activity from the audit log (humans and admin only; the log spans projects), and the newest event number. The inbox is server-rendered HTML; no htmx or other script library was needed. Every action is a plain form post with a CSRF token (post, redirect, get), so the page works without script. `app.js` only opens an `EventSource`; when the hub says "inbox-changed" it refetches `/inbox/fragment` and swaps the body, unless the human is typing in a field, in which case it shows "New activity. Refresh" instead of throwing away their text. Events are hints only and carry no content; a reconnecting page gets a `resync` first, so a missed event heals itself.

**D44. Streams hold no database connection while they wait.** The hub has one SQLite connection. A stream waits on the in-process notifier and runs a short query only when it sends. Caps: 4 streams per human, 100 in all (429 beyond that); a heartbeat comment every 15 s keeps proxies from timing it out; the session is rechecked every minute so a signed-out browser's stream ends. `Cache-Control: no-transform` and `X-Accel-Buffering: no` keep proxies from compressing or buffering it. Answering an escalation and accepting or rejecting a task from the web share the code of the API verbs (`answerEscalation`, `rejectTask`), so the two paths cannot drift apart.

**D45. Found with a real browser: `Referrer-Policy: no-referrer` makes browsers send `Origin: null` on form posts.** The origin check refused every login from Chromium, and the unit tests (which set the Origin header by hand) could not see it. Fix: the policy is `same-origin` (nothing leaves the site, but same-site posts keep their Origin), and an `Origin: null` is accepted only together with `Sec-Fetch-Site: same-origin`. Lesson kept: UI changes get a screenshot and a click-through in Chromium, not only httptest. The inbox was checked at 1100 px and 390 px, light and dark.

**D46. Devices and settings pages.** Owners add and revoke devices and manage people; members and viewers can see the device list. ## Milestone B (foundations)

**D50. B1: a job is a root task with its own lead.** `task.kind` is `task` or `job`; a job row is never claimed, never on the task board (`task list` hides it, `job list` shows it), and is closed only by a human (`job close`, or `--cancel`, which also cancels its unfinished tasks). Tasks carry `job_id` (and `parent_id`, equal to it for now); an agent can belong to a job (`agent.job_id`). The one-lead rule became "one lead per job, and one project-level lead": the unique index is `(project_id, COALESCE(job_id, 0)) WHERE role = 'lead'`. Everything that used to message "the lead" now asks `leadFor(task's job)`: the job's own lead, falling back to the project lead when the job has none. `role:lead` from an agent means the lead it reports to (its own job, else the job of the task it is working on, else the project lead); a human who says `role:lead` while there are several is asked to name one. Only humans start and close jobs and move agents between jobs, because those decide what an agent is allowed to see and do. A lead's new tasks go into its own job and it cannot choose another; dependencies must stay inside the job. Agent names stay unique per hub: the `<profile>@<job>-<n>` naming belongs to spawn (milestone C). No `brief_path`, `brief_version` or `budget_json` yet: nothing reads them until D.

**D51. B scope changes from v0.4.** (1) *Confidential* is cut to the column and an off switch: `job new --confidential` is refused unless the hub runs with `HANDLOOM_ALLOW_CONFIDENTIAL=1`, because v0.3 section 6 makes "confidential off" the default on a public hub, and a `canRead` gate over content that does not exist until milestone F would be untested code. Tasks of a confidential job inherit the mark. (2) *Member scopes* needed nothing: the viewer role and the owner-only pages were built in A. (3) The lease-based states `dead`, `killed`, `hold`, `relieved` are not added; B uses the existing `offline` (see B3).

**D52. B2: run tokens give attribution and a switch, not isolation from the same user.** An agent can hold a run token (`hvr_...`, only the hash is stored in `agent.run_token_hash`). It is minted when a register asks to rotate (adapter install, `run`) and returned once; a plain re-register keeps the old one. It lives in `<project>/.handloom/tokens/<agent>` (0600), next to `.handloom/agent`; every handloom process the agent runs finds it by walking up from its working directory, and the CLI, the MCP server and the hooks send it as `Handloom-Run-Token` through the link, which still adds the device credential. The hub checks that the token belongs to the agent that is speaking, on `c.agent()` and on the hook endpoints. A wrong or stale token is refused (401); there is no quiet fall-back to the old path, so a stale file shows up at once. The audit log has a `via` column: `run-token`, `device-asserted` (device credential plus a name the caller claims, the old way), or the caller's kind. Rotation is authorised by the device, as registration always was, and is itself audited (`agent.token`), so any process on the device that can run `handloom` can mint a new token for an agent on that device: tokens do not defend against another process of the same OS user, only against a request that arrives from the wrong device, with the wrong agent, after rotation or after the device was revoked. `HANDLOOM_REQUIRE_RUN_TOKEN=1` makes the hub refuse device-asserted agent requests (not the link's own calls, not humans, not the registration that mints a first token); it is off by default because installed adapters and the m0-m2 scripts use the old path. Expiry by lease arrives with B3. Checked: Go tests (borrowed tokens, other device, rotation, revoked device, the require switch), a real headless Claude Code turn whose inbox read and state changes are audited as `run-token`, and `m0.sh`.

**D53. B3: the supervisor is the hub's timer plus the link's word about terminals.** The link (which can see tmux and herdr panes) tells the hub every `LiveEvery` (20 s) that an agent's terminal still exists (`POST /agents/{name}/heartbeat`, device-authorised). That renews `agent.lease_expires_at` (90 s, `--agent-lease`). When `Sweep` (the hub's existing 5 s ticker) finds a lease past due, it marks the agent `offline` with reason `lease_expired`, once. A returning heartbeat turns `offline` into `unknown` until the agent's own hooks report. Agents with no terminal (headless, shell) have no lease and never expire: they are resumable, so there is nothing to vouch for. The check is `tmux display-message` or `herdr pane get`; a failed check counts as dead, and ninety seconds allow about eight misses. When a lead goes offline (lease expiry, or its session-end hook) with work unfinished (a job's lead: open, claimed or submitted tasks of the job; the project lead: claimed or submitted tasks without a job), the hub records `job.lead_lost`, sends a push (a link and "the lead of job #N went offline with k task(s) unfinished", never task content) and the inbox shows a needs-you item with the command. A lead with nothing left is not an alarm. `handloom job resume <job> --lead <agent>` (human): the old lead becomes a worker without a job, its unread mail is forwarded to the new lead (marked as forwarded, and marked read for the old one), the new lead is told the state of the board; the task graph is the whole state, so nothing else is rebuilt. An agent that already leads something cannot be given a second job. A worker with no job asking for `role:lead` reaches the lead of its current task's job, else of its latest task in a job that is still open, else the project lead. Divergence from the B2 plan: a run token does not expire with the lease, because the lease says "the terminal exists", not "the holder is gone", and a laptop that sleeps should not lose its token; rotation and device revocation remain the ways to end one. No `dead`/`killed`/`hold`/`relieved` states: `offline` carries the meaning until spawn exists.

**D54. Found by `b.sh`: `tmux display-message -t <gone pane>` succeeds.** It exits 0 and prints an empty line, falling back to the current pane, so an exit-status check would have kept every dead terminal "alive" forever. `Tmux.Alive` now requires the answer to be the very pane asked about; `herdr pane get` does fail properly (`pane_not_found`, exit 1). Also found: the wake ladder runs every `--tick` (10 s by default) and is what vouches for terminals, so the agent lease must stay well above the tick; the check script runs the link with `--tick 1s --live-every 2s` against a 6 s lease. `b.sh` (about 8 s, one machine, tmux, shell agents) covers B: a job with its own lead and two tasks, the lead's terminal killed, the hub marking exactly that agent offline, the push naming the job without its content, the inbox item and the audit rows, then `job resume` giving the new lead the board and the old lead's unread mail, and the worker's next `role:lead` message following the job to its new lead. It also shows `run` agents authenticating with run tokens. Not covered by it: a real agent CLI as the lead (that needs `m1.sh`/`m2.sh` and the Mantis login).

## Milestone C (spawn, profiles, skills)

**D55. C1: spawn is a request to a link, and the link owns the terminal.** `handloom spawn <name> --kind claude` (lead into its own job on its own device; human with `--device` and optionally `--job`) writes a `spawn` row (pending) and wakes that device's long-poll (a `spawn.requested` event addressed by device id). The link claims it (pending to launching, which the hub grants once, so a restarted or duplicate link cannot start it twice) and opens a window in a tmux server of its own (`tmux -L handloom`, `--tmux-socket` or `HANDLOOM_TMUX_SOCKET` to change it), in a directory it creates under `<home>/work/<job>/<name>`. The window runs `handloom spawn-exec <id>`, which installs the adapter through the same code as `adapter install`, reports `started` with the pane's wake target, and becomes the agent CLI through `run`. So a spawned agent is registered with its own pane, and the wake ladder, the liveness lease (B3) and the lead-lost alarm work for it unchanged; its wake target comes from the link's tmux server, never from whoever asked. Unattended means no prompt can ever stop it: Claude Code runs with `--permission-mode dontAsk`, an explicit tool allowlist (Read, Glob, Grep, Write, Edit, `Bash(handloom:*)`), and `--setting-sources project,local`, so the user's global settings do not apply and the adapter's `.claude/settings.local.json` does. The "trust this folder" question is answered in advance by setting `hasTrustDialogAccepted` for the work directory in `~/.claude.json` (only when that file exists, only for the directory the link made, other keys untouched). Verified headless: a `--disallowedTools` entry and a `deny` rule in `settings.local.json` (with `--setting-sources project,local`) both refuse `rm` and win over an allow rule. Hub-supplied strings never reach a shell: the hub names an agent and a kind (the name is checked against `[A-Za-z0-9][A-Za-z0-9_.-]{0,63}` by the hub and again by the link, the model against a narrow pattern), the command comes from a fixed table, and the pane command quotes everything. Cap: five agents running or starting per job (`MaxSpawns`); a request nobody starts within 90 s fails ("is its link running?"). Only kind `claude` can be spawned so far. Not yet: profiles (what an agent may do and know, C2), codex (C3), the web form (C4).

**D56. C2: a profile is a directory, a hub row per version, and files and flags in the agent's work directory.** `profile.yaml` (name, description, kind, runtime, model, tools), `PROMPT.md` and `skills/<name>/SKILL.md` (with any other files of the skill). The hub stores each version immutably (database triggers refuse updates and deletes) with a hash of its content; saving an unchanged profile makes no new version. Only the owner or the admin writes profiles, because a profile can allow a shell. A spawn is pinned to the exact name, version and hash it was requested with; the device fetches that pinned version for its own spawn only, recomputes the hash and refuses a mismatch, and refuses skill paths that are absolute, contain `..` or backslashes, or would be written through a symlink. Tools are four words every agent CLI can be asked about: `read`, `edit`, `shell`, `web`, plus `deny_commands` (up to three plain words per entry; no quotes, brackets or wildcards, because the entry becomes `Bash(<cmd>:*)`). For Claude Code the profile becomes `--permission-mode dontAsk`, `--allowedTools` (always including `Bash(handloom:*)`), `--disallowedTools`, `--setting-sources project,local` and `--model`; skills go to `.claude/skills/`, the prompt into the instruction file's block. The profile's page and `profile check` list, in words, what is enforced and what is not (file paths, time, turns and cost are not). `runtime: local` is how a profile says its model runs on the owner's own machine; a confidential job refuses to start an agent from anything else (and from no profile). Checked with a real Claude Code (`c2.sh`): the denied `rm` is refused and the file survives; the profile's skill is visible and a decoy skill in the user's global `~/.claude/skills` is not; the profile's prompt is followed. Divergences from the plan: the manifest for user-added CLIs, `adapter test`, `profile try` and per-device approval of profile hashes are not built (the device trusts the hub; hub-supplied profile content reaches argv as plain elements, never a shell, but a compromised hub could therefore choose what an agent may do on every linked device: approving profile hashes on the device is the mitigation, deferred).

**D57. C4: Agents and Profiles pages.** Agents lists agents and recent starts and has the start form (a member or the owner; a viewer sees the page without the form). Profiles lists the library; a profile's page shows what it enforces and, for the owner, an editor with the password asked again; saving makes a new version. Editing keeps the other files of a skill, clearing a skill's text removes it. Everything a profile contains is rendered escaped (checked with script and image payloads in prompt and skill text).

**D58. C3: Codex is spawned like Claude, with what its CLI can actually do.** `spawn-exec` for kind `codex` runs `codex --enable hooks --dangerously-bypass-hook-trust -a never -s <workspace-write|read-only> [--search] [--model M]` and the handloom verbs as an MCP server (`-c mcp_servers.handloom.*`, tools pre-approved, `HANDLOOM_HOME` and `HANDLOOM_AGENT` in the server's environment, TOML-quoted), because Codex's sandbox blocks the link's socket for shell commands and MCP tools run outside it (D23). A Codex profile therefore says less than a Claude one, and refuses what Codex cannot do instead of dropping it: no `deny_commands` (the sandbox limits files and network, not commands), no skills (Codex's skill loading was not verified), and `shell` must be listed (it cannot be taken away); `edit` selects `workspace-write` (else read-only), `web` selects `--search`. The profile page and `profile check` print what each CLI enforces. Found by `c3.sh` with a real Codex on Mantis: a fresh work directory stops Codex at "Trust this folder?", and the link's first nudge, typed into that dialog, made Codex quit. Fix: `spawn-exec` records the directory as trusted in `~/.codex/config.toml` (`[projects."<dir>"] trust_level = "trusted"`, exactly what Codex writes itself, only when the Codex directory exists, nothing else touched). The same run showed that a dead pane must not look alive: the link's tmux server now sets `remain-on-exit failed`, so an agent CLI that dies with an error leaves its screen behind to be read, and `Alive` also asks `#{pane_dead}`. `c3.sh` (two machines, a few cents of Codex usage) passes: Codex starts on Mantis in the link's own tmux server, reads its inbox through MCP with its run token, follows the profile's prompt, writes in its work directory, and is refused when it tries to write outside it.

## Milestone D (jobs from a brief, repositories, checking work)

**D59. D1: a repo job, a worktree per agent, and a lead the job starts itself.** `job new --repo <path> --verify <cmd> --device <D> --lead-profile <P>` records the repository path (absolute, on one device), an optional verify command (one line, run later by the device) and that device on the job, and starts the job's lead from the profile (`lead-<id>` unless named) as a spawn with role `lead`. The role is human-only on the API; a lead cannot start leads; a job has one lead. When the link starts a spawn for a job with a repo it first runs `git worktree add -b job/<id>/<name> <workdir> HEAD` in the repository (the directory it just made is empty, which git 2.43 accepts; an existing branch of that name is reused), so each agent works on its own branch of the real repository and cannot trip over another's files; uncommitted changes in the repository are not carried over (the worktree is the last commit) and the link logs it. `spawn-exec` records the commit the worktree started from in `.handloom/scope.json` (so what an agent changed can be told from what was there), and sets git's author and committer to the agent's name. Agents of a repo job start on the job's device; another device is refused. When the hub makes the spawned agent a lead (at `started`), `spawn-exec` writes the instruction block again so it carries the lead's guidance; that is why a lead's `CLAUDE.md` is written twice. The hash of a stored profile is pinned by a test, so new fields in a profile cannot make existing spawns fail. Known limits, to be fixed after D: a task's dependency is ordering only (worker 2's worktree was cut before worker 1's branch existed, so it cannot see worker 1's work), and nothing merges task branches into the main branch yet.

**D60. D2: the scope check runs on the device, at submit, from the link's own copy.** A profile may list `write:` patterns (relative to the worktree; `*` inside one path element, `?` one character, `**` any number of elements, a trailing `/` for a whole directory; no `..`, no absolute paths). In a repo job the link puts itself in front of `POST /v1/tasks/{id}/submit` on its socket (a more specific route than the `/v1/` proxy). For an agent whose worktree the link made, it lists what differs from the commit the worktree was cut from (`git diff --name-only --no-renames -z <base>` for tracked changes, committed or not, a rename counting as a delete and an add, plus `git ls-files --others --exclude-standard` for new files) and refuses the submit with the offending paths if any is outside the patterns; the agent has to revert them. The files handloom and the agent CLIs write into a work directory (`.handloom/`, `.claude/`, `.codex/`, `.pi/`, `.opencode/`, the top-level `CLAUDE.md` and `AGENTS.md`) are not counted; a nested `src/CLAUDE.md` is. The link keeps the base commit, the patterns and the directory in `<home>/scopes/<agent>.json`, not in the worktree, because the agent can edit everything inside the worktree, including `.handloom/scope.json`; the patterns come from the profile version the spawn is pinned to. A check that cannot run (the worktree is gone, git fails) refuses the submit rather than waving it through. Agents the link did not start and profiles without `write` are not checked, so the earlier flows are untouched. A refusal is reported by the link with its own credential (`POST /v1/device/scope-refused`: the hub records `task.scope_refused` with the paths and tells the agent's lead); that route is blocked on the agent-facing socket, so an agent cannot file one. What this is not: the check looks at what the agent has changed when it submits; it does not stop it writing elsewhere while it works, and the profile page says so.

**D61. D3: the device checks what was submitted, and the lead cannot accept what failed.** A job's `verify` command is a one-line shell command written by a human and stored on the hub. When a submit from a link-started agent of that job goes through, the link runs it (`sh -c`, in the agent's worktree, a plain environment without the link's own variables, a process group so a timeout stops everything, 10 minutes by default) and reports the exit code, a timeout flag, the last 3000 bytes of output and the SHA-256 of the whole log, which stays on the device (`<home>/verify/`). The hub stores one check per task for its current submission (a new submit or a reject clears it), shows it in `task show` as "checked by device X (not by the agent)", on the inbox's review card, and tells the lead. In a job with a verify command an agent (the lead) cannot accept a task that has no check yet or whose check failed or timed out; a human still can, because the human is the one who decides what the check was worth. The report endpoint is blocked on the agent-facing socket (an agent cannot file its own passing result) and the hub accepts it only from the device the agent lives on, for a task the agent owns and has submitted, with the job's own command. Trust: this runs a command from the hub on the device, like a profile does; the device trusts the hub for it (per-device approval is deferred, D56). Found while testing: the link tests wrote scope and verification files into the real `~/.config/handloom`; the fixture now points `HANDLOOM_HOME` at a temporary directory.

**D62. D4: Jobs pages.** Jobs lists jobs with their lead, task counts, repository and device. New job takes a title, a brief, the device, an optional repository and verify command, and the lead's profile (and a confidential box only on a hub that allows it); it is the same code as `job new` (a viewer may not). A refused form is shown again with what was typed and leaves nothing behind. A job's page shows the brief, what the device checks, each task with its owner, dependencies, evidence and the device's check (a failed check in red with the end of the output, a passed one in green), the team with states, recent activity, how to look over an agent's shoulder (`tmux -L handloom attach -t handloom:<name>`, run on that device; there is no browser terminal), a way to hand the job to another agent when the lead stopped, and cancel. When every task of an open job is done the job page and the inbox ask for it to be closed (a `job-done` item in the digest). Task review stays in the inbox. A handler that failed without writing anything now gets a plain error page instead of an empty one.

**D63. D5/D6: lead guidance, end-to-end check, Codex, deploy.** `test/e2e/d.sh` starts a job on a toy repository with one command and a prescriptive brief; a real Claude lead plans two tasks (the second depends on the first), starts one worker from a profile, the worker edits its own worktree, commits and submits, the device checks each submission, the lead accepts, and the job asks to be closed with no human action after `job new`. It then makes one out-of-scope edit and sees the submit refused. Result: 3 of 3 runs passed (about 7 minutes each), so the kill criterion (lead mis-plans 3 of 5) is not hit. The brief was prescriptive; a vague brief is untested. Codex finding: in `workspace-write` Codex cannot write the repository's `.git` (a worktree's index lives there; `--add-dir` and `writable_roots` did not help), so git commit fails inside it. For Codex agents the link therefore commits their changes at submit (no hooks, the agent's own name). Codex plus worktrees is tested only to that point, not end to end. Deployed as image a-b3e171d; migrations 11 and 12 applied (snapshot `pre-v12.db`; 11 and 12 ran together).

**D64. Merging accepted work.** Accepting a task in a repository job queues a merge for the job's device (table `merge`, migration 13; the hub only keeps the list and the outcome). The link merges the owner's branch `job/<id>/<agent>` into `job/<id>/integration` with `--no-ff` in a worktree of its own (`<work>/job-<id>/_integration`, started from the base commit), without hooks, then runs the job's verify command there. A conflict is aborted; a failed check resets the branch to where it was, so the integration branch always holds merged and checked work. Either way the lead gets a message (create a task for that worker to merge the integration branch into its own, resolve, submit) and the human sees a needs-you item; a later accept of fixed work retries. Nothing touches the repository's own branches or its checked-out files: the human merges `job/<id>/integration` when satisfied. Merge endpoints are blocked on the agent socket. Task order is still only ordering: a worker does not see another worker's merged files unless it merges the integration branch itself.

**D65. Evidence for the lead and for Codex.** (1) Codex worker under a Claude lead on Mantis (`test/e2e/d_codex.sh`): passed. The lead started a Codex worker, Codex wrote its file and submitted through MCP, the link committed for it, the device checked, the lead accepted, and the device merged into `job/1/integration` (about 6 minutes, no human input). (2) Vague brief (`test/e2e/d_vague.sh`, one sentence of intent: add a `--name` option, document it, keep ./check.sh green): 5 runs. In all 5 the lead started one worker, made one task, got a passing device check, and the merged integration branch is correct (`--name` works, README documents it, check passes). The script reported 5 failures because of a harness bug (it tried to check out a branch already checked out in the device's integration worktree); fixed, and the five saved results were re-judged by the same check: 5 of 5 right. The kill criterion (3 of 5 mis-plans) is not hit. Caveat: the task was small enough that one task and one worker is the right plan; a multi-part vague brief with dependencies is not tested, so "the lead plans well" is shown for small jobs only.

**D66. Multi-part vague brief.** `test/e2e/d_multi.sh`: two features in one file (`--shout`, `--times N`, must work together, document both, check must pass), 3 runs, real Claude. 3 of 3 passed: the merged integration branch supports both options together, README documents both, check green, no human input. Plans varied (2 workers + 2 tasks; 1 worker + 1 task; 1 worker + 2 tasks), all sound. All merges were clean; the conflict path is covered by the link unit test only, not by a real lead recovering from one. With D65 that is 8 of 8 small vague jobs planned and finished correctly.

**D67. First-run help.** The README now opens with a four-stage quick start (hub, join each machine, profiles, first job); it had said the web board did not exist. The inbox shows a "Get started" card while any of: a machine has joined, a profile exists, a job exists, is still missing (not for viewers); it vanishes when all are done. `handloom doctor` runs on a machine and checks the link and hub, git, tmux, and each agent CLI (installed, and logged in where handloom can tell: Claude by its credentials or account file, Codex by its auth file; Pi, OMP and OpenCode are reported as installed only). It exits 1 only for hard problems: no link, no git, no tmux, or no usable agent CLI at all. It changes nothing.

**D68. Client knowledge and base branch (milestone F, first part).** A job may name a knowledge repository (an absolute path on its device) and a base branch (`job new --knowledge PATH --base BRANCH`, and the same two fields on the New job form; migration 14). Every agent of the job gets a detached checkout of the knowledge repository at `.handloom/knowledge/`, inside its own work directory, so every agent CLI's sandbox can reach it and the code pipeline ignores it (`.handloom` is excluded from the scope check and the Codex autocommit). Agents whose profile runtime is not local get it without its `confidential/` folder (sparse checkout, removed if that fails; the spawn fails rather than leave it). Agents edit notes in that checkout; these are proposals. When a task is accepted (the owner's and the lead's) and when the job closes (everyone's), the device commits the agent's changes in its checkout under the agent's own name, without hooks, and cherry-picks them onto the branch `job/<id>` of the knowledge repository, made in a link-owned worktree; a conflict is aborted and reported, never half-applied. **D105. Projects, stage two: a fresh base for each job, and the pull request's status.** **Fresh base.** When a job that belongs to a project (`task.codebase_id`) gets its first agent on a machine, the link, before the first worktree is made (`launch`, once per job and process; the hub marks the spawn `fresh_base` only while the job has no recorded base, so later agents of the job and a restarted link do not move the base in the middle of a job), runs `git fetch origin` and then moves the clone's local branch for the job's base (the job's base, else the branch the clone has checked out) to `origin/<base>` only if that is a pure fast-forward: `git merge --ff-only` in the folder where the branch is checked out (main clone or another worktree) and only when that tree has no uncommitted changes to tracked files, `git update-ref` with the old value as a guard when it is checked out nowhere. Never forced, never a merge, rebase or reset, never blocks the job (fetch 60 seconds, other git commands 30). The outcome is a record on the job (migration 18, appended: `task.base_state`, `base_detail`, `base_commit`), reported once on `POST /v1/jobs/{id}/base {status, detail, commit}` (device-only, the job's own device, a job of a project, once; the link refuses the path for agents on its socket): `fresh` (fast-forwarded, or already current, with the short commit and the number of commits moved), `stale` (fetch failed, origin lacks the branch, the base is not a local branch, or uncommitted changes on the checked-out branch; the detail says which, in words, and that the job starts from the copy as it is) and `diverged` ("this machine's copy of <base> has commits that are not on origin; the job starts from it as it is": the local branch is not an ancestor of the remote one, so it has its own commits and nothing is touched). No `gh`, a failing `gh` or an answer it cannot read: skipped without a word, the publish keeps its link. **D109. A remote MCP connector: paste one address into Claude, sign in, nothing installed.** A user could not use the stdio settings of the Connect page: there was no `handloom` program on that Mac, and Claude Desktop does not use the shell's PATH to find one. **What changed.** The hub is now a remote MCP server at `<HANDLOOM_BASE_URL>/mcp` and its own OAuth 2.1 authorization server, so claude.ai, Claude Desktop and Claude Code (`claude mcp add --transport http handloom <hub>/mcp`) connect with one address and a sign-in. **Transport.** Streamable HTTP with plain JSON answers: `POST /mcp` carries one JSON-RPC message; a request gets one `application/json` body, a notification or a client's answer gets `202` with no body, `GET`, `DELETE` and other methods get `405` (there is no event stream and nothing is held open, so no proxy setting matters). A batch is refused (the 2025-06-18 revision removed them). Both generations are served from the same code: the classic `initialize` / `notifications/initialized` flow (the `Mcp-Session-Id` is never issued and always ignored), and the newest stateless style (a request with no earlier `initialize`, `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`): those headers are accepted and never required; an `Mcp-Method` that differs from the body's method is `400` with a JSON-RPC error; an unknown `MCP-Protocol-Version` is `400` listing the supported ones. Supported versions: 2026-07-28, 2025-11-25, 2025-06-18, 2025-03-26 (a client's version is echoed when listed, else the newest is offered). `resources/list`, `resources/templates/list` and `prompts/list` answer with empty lists so a client that probes does not see an error (only over HTTP; the stdio server is unchanged). An `Origin` header, when present, must be the hub's own origin or `https://claude.ai`, `https://*.claude.ai`, `https://claude.com`, `https://*.claude.com`, else `403` (the browser-origin defence against DNS rebinding; servers calling servers send none), checked before the token. **Tools.** `internal/mcp` is split into the transport-agnostic `Server` (JSON-RPC dispatch and the tool table; `ServeTools` is the stdio framing, `HandleHTTP` the HTTP one), and the connector offers exactly `OperatorTools(false)`: same names, descriptions and annotations as `handloom mcp --operator`, and no approvals (`handloom_task_accept`, `handloom_task_reject`, `handloom_answer`, `handloom_job_close` are absent from `tools/list` and are "unknown tool" if called by name). The hub cannot import the command line (the cli imports the hub), so `hub.Options.OperatorRun` is a hook the cli provides (`internal/cli/connector.go`): it runs a tool's argument list through the real command line, in the hub's process, with an `http.RoundTripper` that calls the hub's own handler and the connected app's access token as the bearer. For that, `env` got an optional pre-made client (`cli.MainWith`) and the 38 `conn()` calls became `e.conn()`: the token is never read from the process environment, so concurrent calls for different people cannot mix. There is one tool table and one enforcement point, the hub's allowlist. A tool's failure is a tool result with `isError`; a panic is caught; the token is replaced by `[token]` in anything that comes back. The `/mcp` request settles who is asking in a short transaction of its own before the tool runs (the database has one connection). **Who is asking.** Unauthenticated, invalid, expired or revoked tokens get `401` with `WWW-Authenticate: Bearer resource_metadata="<BASE>/.well-known/oauth-protected-resource"`. Only operator principals may use `/mcp`: the issued access token (`hvt_`) and, decided on purpose, the static D80 `hvo_` token too (the same principal with the same allowlist, so it adds no power, and it helps testing and people who already have one). The admin token, a person's own `hvh_` token, a machine's credential, agent requests, and OAuth codes and refresh tokens all get the same `401`. **Same allowlist.** An access token authenticates as `principal{kind: human, operator: true, via: "connector"}`, so the existing check in `handle` (`operatorCalls`) refuses everything but reading, starting a job and messaging an agent, with `403` and a `denied` audit row, exactly as for `hvo_`; the scope table gets no new row. The D80 token (one per person, a new one replaces it) is untouched: connecting Claude does not disconnect a Claude Desktop stdio setup, and the reverse. **Discovery.** `/.well-known/oauth-protected-resource` (also `.../oauth-protected-resource/mcp`): `resource` `<BASE>/mcp`, exactly one `authorization_servers` entry (`<BASE>`), `scopes_supported` `["handloom"]`, `bearer_methods_supported` `["header"]`. `/.well-known/oauth-authorization-server` (also `/.well-known/openid-configuration`, same document): issuer `<BASE>` with no trailing slash, `authorization_endpoint` `/oauth/authorize`, `token_endpoint` `/oauth/token`, `registration_endpoint` `/oauth/register`, code only, `authorization_code` and `refresh_token`, S256 only, `none` as the client authentication method, and `authorization_response_iss_parameter_supported` true (the redirect carries `iss`, RFC 9207). `<BASE>` is `HANDLOOM_BASE_URL`; without it (plain `HANDLOOM_INSECURE`) the connector is off with a `404` that says what to set, because an issuer must be a fixed, trusted value, never the request's `Host`. **Registration (RFC 7591).** `POST /oauth/register`, unauthenticated JSON of at most 4 KB, 10 a minute per address: public clients only (a client secret or any method but `none` is refused). Accepted redirect addresses: exactly `https://claude.ai/api/mcp/auth_callback`; `http://localhost:<port>/<path>` and `http://127.0.0.1:<port>/<path>` (Claude Code); and exact https addresses the owner lists in the new setting `HANDLOOM_OAUTH_REDIRECTS`. The client id is random (`hvc_...`), the name is stripped to 60 printable characters; at most 500 apps, with those that never completed a grant removed after 7 days. **Consent.** `GET /oauth/authorize` needs `response_type=code`, a registered `client_id`, a `redirect_uri` equal to a registered one (a loopback address matches on any port, nothing else about it may differ: RFC 8252), PKCE with S256 (plain is refused), `resource` (when sent) equal to `<BASE>` or `<BASE>/mcp`, scope (when sent) `handloom`. A wrong app or redirect address gives a plain page and nothing is redirected; any other fault goes back to the (valid) redirect address as an OAuth error with `state` and `iss`. A person who is not signed in goes to the sign-in page and comes back (`/login?next=`, accepted only for an `/oauth/authorize?...` path, so it is no open redirect). The consent page is server-rendered with the strict CSP (one change: `form-action` also names the app's redirect origin, because browsers check it against the redirect that follows the post), a CSRF token and the password step-up as for D80's token; it says which app wants to connect as whom, what it will and will not be able to do, and that it can be disconnected. Owners and members only (a viewer is refused in words). Allow makes a grant and a single-use code (32 random bytes, stored hashed, valid 2 minutes, bound to the app, redirect address, challenge, person and resource), audited `app.connect`; Cancel (no password needed) redirects `error=access_denied`, audited `app.deny`. **Tokens (RFC 6749, OAuth 2.1).** `POST /oauth/token`, form-encoded, rate limited by address and by app: `authorization_code` (the verifier is 43 to 128 characters and is checked with S256, in constant time; the redirect address must be the one the code was made for) and `refresh_token`. An access token lives an hour; a refresh token 60 days and slides, because each refresh issues a new refresh token and the old one is spent. Seeing a spent code or a spent refresh token again, or a wrong verifier, revokes the whole grant (audited `app.revoke`), so everything issued from it stops. Tokens are random and stored only as SHA-256 hashes, compared in constant time; answers carry `Cache-Control: no-store`; errors are RFC 6749 JSON (`invalid_request`, `invalid_client` 401, `invalid_grant`, `invalid_target`, `invalid_scope`, `unsupported_grant_type`). **Records.** Migration 24, appended: `oauth_client`, `oauth_grant` (person, app, when allowed, when first used, last used, revoked) and `oauth_token` (kind code, access or refresh; hash; expiry; used; challenge; redirect address; resource). A grant is "connected" only once its code was traded. **The Connect page.** A new first section "Connect Claude (nothing to install)" shows `<BASE>/mcp` in a copy box with three steps for claude.ai and Claude Desktop and the `claude mcp add --transport http` line for Claude Code; then "Connected apps" (name, connected, last used, Disconnect). Disconnect is a POST with the session's CSRF token and no password, because it only takes access away (unlike making an `hvo_` token, which asks for the password); it revokes the grant, `/mcp` answers `401` at once for its tokens, audited `app.revoke`. The earlier stdio block moved under a collapsed "Advanced: run a program on your computer", with the warnings that the program must be installed on that computer and that Claude Desktop does not use the shell's PATH, so the command field needs the full path (`command -v handloom`). **Not done, on purpose.** (1) Client ID Metadata Documents (CIMD): the hub would fetch a URL chosen by the client, which is a server-side request forgery risk; dynamic registration is used instead, and `client_id_metadata_document_supported` is not advertised. (2) Approvals over the connector: accepting, answering and closing stay with the person in the web UI. (3) Per-tool scopes: one scope, `handloom`. (4) Redirect addresses of other AI products beyond what the owner lists in `HANDLOOM_OAUTH_REDIRECTS` (Claude's `claude.com` spelling, for one, is not built in). (5) IPv6-only hosts and `http://[::1]` loopback addresses. (6) JSON-RPC batches, an event stream, `Mcp-Session-Id`. (7) CORS on the discovery documents, the token and the registration endpoints: a browser-based inspector cannot use them (Claude connects from servers and from programs, not from a page; `/mcp` itself answers the preflight for the allowed origins). (8) A grace period for a refresh retry whose answer was lost: a reuse revokes, as OAuth 2.1 asks, and the person connects again. **Known unverified.** No real Claude client (claude.ai, Claude Desktop or Claude Code) was available to the builder. Everything above is built to the specifications and tested against a Go and a Python client of the builder's own (the unit tests, and `test/e2e/connector.sh` against a real hub process and the real command line).
