## Candidate directions

### D1. Harden the core: correctness guarantees before features (effort M)

**Thesis.** Handloom's durability is lease-based supervision around git, and 'durable' means a crash neither loses nor duplicates work. Make the core provably safe under crash, retry and concurrent resume before adding any surface area. This is a deliberate do-less direction.

**What it means.** Add an epoch/fencing token to leases so an expired or reassigned agent cannot submit or accept. Add idempotency keys on submit, accept, answer and close. Make answering an agent question consume-once. Write the resume policy down, in the style of Claude Code's rule: never silently re-run a cut-off effect, tell the resumed agent it was interrupted, and require it to verify state first. Require a handoff note per task (state, tried, next step, how to verify) that the hub stores and the link writes into the worktree. Add a no-progress and stuck exit, which closes the F1 hole where a stuck agent that claimed nothing is invisible. Enforce wall-time, turn and owner-priced cost limits per task. Pin the profile version for in-flight jobs and document what an upgrade of the hub or link does to running work (D95 lists it as untested). Extend the m0-m2 and b.sh fault-injection suites to cover each guarantee. Publish a plain statement of what survives a crash (task graph, committed branches, evidence) and what does not (uncommitted changes, agent context, non-git side effects).

**Enterprise value.** Gives an enterprise buyer a defensible reliability claim that mature frameworks fail on (the conformance preprint reports duplicate effects on concurrent resume), and removes the 'unattended means unsafe' objection. It is also the prerequisite for any scheduled or triggered work. It needs no new infrastructure and fits one maintainer.

**Main risk.** It adds no visible feature, so it does not move a procurement checklist (SSO, isolation, triggers). The main supporting study is a single-author, un-replicated preprint. Vendor CLIs are absorbing per-session durability, so the guarantees only matter at the hub and task layer, and the work could be seen as polish.

### D2. Real isolation: container/microVM mode behind the Isolator seam (effort L)

**Thesis.** The largest finding a security reviewer will raise is that agents run as the link's OS user with unattended flags, and repo content is itself an execution surface. Closing it is the first enterprise milestone, and Handloom should consume existing sandbox technology rather than invent any.

**What it means.** Build the container isolator behind the existing seam: OCI-runtime-agnostic (runc hardened by default, runsc or kata selectable, Docker sbx or K8s Agent Sandbox as later backends). Default-deny network, a per-profile egress allowlist through a proxy, no Docker socket, and no host home directory. Rework the credential design before writing the isolator: the box does not hold secrets, and a proxy injects them for cloud-CLI profiles, while local-model profiles carry no cloud credential at all. Handle the .git exposure (a read-write bind mount lets a box damage history). Stop pre-trusting directories and loading project-level agent settings in isolated mode. Add a Rule-of-Two indicator on each profile (untrusted input, sensitive access, outward action). Add device-side verification of profile hashes (deferred in D56) so a compromised hub cannot widen what agents may do. Test all five CLIs under default-deny egress, since their telemetry, update checks and web tools are untested. Document the runtime versions tested.

**Enterprise value.** Removes the most damaging security-review finding and the gap against Cursor, OpenHands, Coder and Docker sandboxes. It makes unattended and triggered work defensible and gives egress control for the Rule of Two. Device-side profile-hash approval closes hub-as-single-point-of-trust.

**Main risk.** A half-built 'container mode' (default container, bind-mounted repo, open network) would be weaker than the honest 'not built' status and would be read as a security claim. Five CLIs each have their own login home, hooks and sandbox quirks. A hostname-allowlist proxy can be bypassed by domain fronting, so egress control must not be marketed as exfiltration prevention. Maintenance load is high for one person.

### D3. Identity and team isolation: OIDC, scoped teams, separation of duties (effort L)

**Thesis.** Enterprise adoption is gated by who can see and approve what, not by agent quality. Make one hub safely usable by several teams by federating identity first and scoping everything to teams second.

**What it means.** Add OIDC login with group-to-role mapping, with SAML only if a buyer demands it and SCIM later. Add per-team scoping of jobs, machines, profiles, knowledge repos and alert topics inside one hub (issues #13, one alert topic per hub), using group claims as the isolation key. Add optional separation of duties (a job's starter cannot accept; a confidential job needs a second approver). Give agents, devices and operator tokens short-lived, audience-bound credentials with a named human owner (sponsor), and add a token and agent inventory report. Add question timeouts, reminders and escalation to a second person, plus delegation. Until team scoping ships, state plainly that the answer is one hub per trust boundary.

**Enterprise value.** Turns Handloom from a single-team tool into something an IT department can approve. SSO is cited as a consistent procurement blocker, and per-team isolation is the largest structural gap. Sponsor-owned identities and separation of duties match auditor requests (ownership, scoped autonomy, oversight points).

**Main risk.** Authorization bugs in a SQLite hub where every query now needs a team filter can leak across teams, and that is worse than having no isolation. SSO demand evidence is low-confidence and secondary. SOC 2 expectations cannot be met by an open-source project, so the buyer's controls carry the review. It is a lot of plumbing with no agent-facing benefit.

### D4. Safe automation: schedules and triggers that only ever create reviewable jobs (effort L)

**Thesis.** Schedules, webhooks and source-control events are now table stakes at every vendor. A trigger should do one thing only: instantiate a saved job template, never act directly. The review queue stays the product.

**What it means.** Add job templates (profile, brief, repo, check command) and a trigger table in the hub: cron, a signed inbound webhook with a per-automation token, and optional GitHub or issue events. Fires are idempotent, with a dedupe window and a skip-if-open-job-for-key option. Enforced safety envelope: per-run and per-day caps on wall time, turns and owner-priced cost, max concurrent and queued runs, a consecutive-failure circuit breaker, a dry-run mode that creates the job but starts no agent, and kill switches at automation, all-automations and hub level. Trigger payloads are stored as untrusted data and never choose the profile, device or check command, and triggered jobs default to least-privilege propose-on-branch profiles. Each automation has a named owner and its own identity. Audit every fire, skip and cap hit. Ship first the schedule the project already needs: the knowledge-repo librarian (D68). Next come scheduled chores, PR review, alert-to-draft-PR and migration fleets. Document how an external Temporal or n8n flow can start jobs through the operator API instead of building an engine.

**Enterprise value.** Closes the largest functional gap against Routines, Cursor Automations, Codex automations and GitHub Agentic Workflows, and offers what they do not: team-owned, auditable schedules (hosted routines run as the creator's identity and are per-account), multi-vendor, self-hosted and confidential-local. It uses the evidence-backed shapes (chores, review, migrations) that end at human review.

**Main risk.** It turns a human-in-the-loop tool into one that spends money and touches repos unattended, in a pre-1.0 project with no case studies. Inbound webhooks need a public hub endpoint, which widens the attack surface of a hub designed to have no shell. Without D1, D2 and D3 it multiplies exposure (prompt injection through payloads, duplicates, every signed-in person seeing every automation). More jobs can swamp review capacity. Hosted vendors will out-ship it on integrations.

### D5. Evidence and compliance layer: flight recorder and control mapping (effort M)

**Thesis.** Auditors certify organisations, not tools, so the winning move for a self-hosted harness is to be the best source of evidence and enforcement points, and to be honest about what it cannot certify. Turn the audit log into a flight recorder with a published control mapping.

**What it means.** Hash-chain audit rows with periodic signed checkpoints, add NDJSON/OTLP and syslog/webhook export, configurable retention and a verification command. Per task, keep the diff, path-policy decision, check output, accept or reject decision and who made it, with optional opt-in transcript capture that stays local and is redacted by default. Add W3C trace context (a TRACEPARENT per job passed to agents) and OTLP spans under a Handloom-owned namespace, with an opt-in gen_ai.* mapping because those conventions are still pre-stable. Produce an inventory report (agents, profiles, devices, tokens). Publish a control-mapping page against OWASP ASI01-ASI10, the NIST drafts, the IMDA framework, and the auditor lists, with three columns: enforced, only instructed, not built. Add an SBOM and govulncheck to the release workflow, extending the existing Sigstore work. Optionally pin skills, MCP server definitions and CLI versions the way profiles are pinned.

**Enterprise value.** Directly answers the security questionnaire items that are currently weak (log not chained, signed or exportable, no inventory) while building on a differentiator the repo already has (honest 'what it cannot enforce' documentation, signed releases). It pairs well with the human-only approval story and is cheap compared with identity or isolation work.

**Main risk.** Overclaiming compliance would be wrong and damaging. The standards underneath are drafts (NIST, OTel GenAI Development status, a changing AI Act timeline), so the mapping page needs ongoing upkeep. Transcript capture enlarges what a hub compromise exposes and conflicts with confidential-job promises unless it stays local and redacted. A signed chain is only as trustworthy as the key held on the same hub.

### D6. Deliberate narrowing: the confidential-work harness for consultancies and small regulated teams (effort S)

**Thesis.** Do not chase enterprise breadth against OpenHands, Coder, GitHub and Cursor. Own the narrow ground nobody states: a hub that never runs git, a shell or a model, evidence-gated and human-only acceptance, per-client knowledge repos, and confidential jobs that stay on local models, for teams of roughly 3 to 30 with client-confidential work.

**What it means.** Cut or freeze the enterprise roadmap (SSO/SCIM, remote OAuth MCP, workflow-engine ideas, Postgres) and state one hub per client or trust boundary as the supported model. Invest only in what that buyer needs: a per-client profile, job and knowledge workspace (a lightweight 'client' scope instead of full team RBAC), a confidential-job guarantee that is checked and visible (a job marked confidential cannot start on a cloud profile, with the check enforced in the link and covered by tests), air-gapped install documentation (offline binary, container image, staged model weights, internal git remote), the cost-per-client reporting the command center already supports, and one or two published case studies with real numbers from the author's work. Add a services and support path (paid installation and profile packs) as the sustainability model. Rewrite README and positioning around this buyer and these invariants.

**Enterprise value.** A credible answer for the segment that most values the existing design: client-confidential work, local models, and an auditable human gate. It also fits a single maintainer, since the goal is depth of trust in a small niche, not breadth. Anthropic's self-hosted mode is unavailable under ZDR/HIPAA, which leaves room for fully local setups.

**Main risk.** The niche may be too small to sustain the project, and its demand is not evidenced (no first-hand evidence found of buyers for a cross-vendor layer). Local-model offline operation is eroding as a unique angle (Copilot CLI BYOK with Ollama and vLLM). Buyers still ask for SSO and a vendor with more than one maintainer. The Vibe Kanban shutdown shows free orchestration lacks a business model. Narrowing could close doors to larger customers.

### D7. Standards-native surface: MCP 2026-07-28 migration, remote MCP with OAuth, portable profiles (effort M)

**Thesis.** Stay compatible and make Handloom a good citizen of the converged formats. Update the hand-written MCP server before agent CLIs stop speaking its dialect, then expose a remote operator endpoint that follows the 2026 authorization recipe.

**What it means.** Phase 1 (urgent): dual-mode the stdio MCP server (D29) to support server/discover, per-request _meta version and capabilities, resultType on results and the new error codes, and test each of the five CLIs against both old and new modes, since Codex's coordination loop runs over MCP. Phase 2: remote MCP on the hub as an OAuth 2.1 resource server: RFC 9728 protected-resource metadata, RFC 8707 audience-bound tokens, RFC 9207 issuer checks, and Client ID Metadata Documents rather than DCR, with scopes encoding 'read and start, never approve'. Model long jobs on MCP Tasks vocabulary (working, input_required, completed, failed, cancelled). Track the Enterprise-Managed Authorization extension for later. Make profiles portable: emit both AGENTS.md and CLAUDE.md, keep skills as spec-valid SKILL.md directories, and re-test the Codex skills note in D58. Watch A2A without building it, and plan for the 12-month deprecations (HTTP+SSE, Roots, Sampling, Logging).

**Enterprise value.** Lets enterprise AI apps and IdPs connect to Handloom through the standard route, turns the operator-token model into a governed remote endpoint, and keeps profiles portable across CLIs. The stdio migration prevents a silent loss of coordination for agents.

**Main risk.** MCP is now a rapid-revision protocol (two breaking revisions in eight months) and a solo maintainer must budget for permanent spec tracking. How each CLI falls back against old servers is unverified. Remote MCP is the hub's first public inbound endpoint and widens its attack surface, and without team isolation (D3) a remote token exposes every job. EMA depends on an IETF draft with thin IdP and client support.

### D8. Structured agent attach: protocol drivers beside tmux (effort L)

**Thesis.** Terminal scraping and per-CLI adapters are Handloom's biggest maintenance and churn exposure. Where agents expose a programmatic interface (Codex app-server, ACP), drive them through it, and keep tmux as the fallback.

**What it means.** Add a driver interface in the link with a tmux driver (current), a Codex app-server driver (JSON-RPC over stdio, with threads, turns, approval and sandbox policy as data) and an ACP driver (about 38 native agents plus adapters for Claude Agent, Codex and Pi). Approvals, events, permissions and cost arrive as protocol data and feed the hub's evidence, lease and usage views directly. This reduces dependence on terminal state for leases and wakes and adds clean cancel and steer. Keep profiles, path checks, device-side checks and the human gate as the layer ACP does not provide. Document an 'any ACP agent' path, with the five CLIs as the tested ones. Pin driver versions and add contract tests per driver.

**Enterprise value.** A broader and more robust 'any agent, any model' claim, structured approval and usage data for audit and cost reporting, and resilience when a vendor changes or retires a CLI. It makes the cross-vendor value proposition concrete instead of a list of five adapters.

**Main risk.** ACP remote transport is explicitly work in progress and Codex's non-stdio transports are experimental, so the interfaces move. More drivers means more surface to test for one maintainer. If vendor CLIs expose first-class multi-machine sessions, the hub-plus-link split looks redundant unless neutrality and verification are clearly the value. Protocol-driven agents may bypass some of the hook and wake behaviour Handloom relies on.

### D9. Quality and cost loop: replay, budgets and metrics that gate profile changes (effort L)

**Thesis.** Public coding benchmarks lost credibility in 2026, so the credible measure for a team is its own history. Use data the hub already holds to compare profiles and models, enforce budgets and show where the lead-plus-workers shape helps or hurts.

**What it means.** Replay a saved task or job against a new profile version or model with repeated trials (pass^k), clean worktrees and the deterministic check command, and link results to the profile hash so a profile change can be gated on a regression suite in CI. Enforce job and task budgets (cost ceiling from owner-entered prices, turn and wall-time limits, loop and no-progress detection, a circuit breaker when workers repeatedly fail the check). Add default metrics: accepted-task rate, first-pass check success, rework or rejection rate, merge-conflict rate, time to accept, human-wait time, cost per accepted task, policy-denial counts, abandoned and duplicate tasks. Add tags (team, client, cost centre) shaped for FOCUS-style cost data. Warn when a job fans out workers on a sequential task graph. Pair outcome metrics with sampled human review to blunt Goodhart effects.

**Enterprise value.** Gives managers a way to decide which profile or model to trust, and to cap spend, with evidence from their own work. It also supports the claim that a centralised, evidence-gated shape is the right one (the Google result: 4.4x versus 17.2x error amplification). Enforced budgets are a precondition for unattended work.

**Main risk.** Replay and eval infrastructure can exceed what one maintainer can support, and integration with existing tools is cheaper than building it. Metrics invite Goodhart behaviour such as small safe changes. The Google study used non-coding tasks, and the cost and SLO figures in circulation are vendor or secondary sources. Enforced budgets can halt a nearly finished task or steer to a weaker model.

### D10. Business-workflow platform: starter profiles as scheduled non-engineering automation (effort XL)

**Thesis.** Handloom ships 41 starter profiles, many for non-engineering work, and its gate (evidence, check, human approval, per-client knowledge) fits recurring business processes (reporting, research, document preparation) as well as code. A bet that the harness generalises beyond coding agents. This bet is risky.

**What it means.** Extend jobs to produce non-git deliverables (documents, spreadsheets, reports) with evidence and acceptance checks defined per template. Add scheduled business workflows through the D4 trigger layer: weekly client reports, regulatory-watch digests, intake triage, with knowledge notes proposed on a branch that a person merges. Add a simple form-driven job start for non-technical users (this ties into the profile-creation UX backlog), approval routing by role, and connectors to common sources through MCP. Package industry profile packs for consultancies and finance, and run local-model-only variants for confidential data. Check each workflow with a deterministic validator where possible, and an independent reviewer agent where not.

**Enterprise value.** A much larger addressable audience than coding teams, and it uses an existing asset (the starter profiles) plus the human gate where companies feel the most risk. If it works it differentiates against code-centric tools like Cursor, Devin and Copilot.

**Main risk.** The research found no evidence on non-engineering enterprise automation (the track explicitly did not cover back-office tools like ServiceNow, UiPath, n8n or Zapier agents), so demand and fit are unproven. Evidence checking is far easier for code (tests, diffs) than for documents, which weakens Handloom's central guarantee. It also competes with well-funded workflow vendors and widens scope for a single maintainer. Gartner expects many agentic projects to be cancelled on cost and unclear value.

### D11. Open-core commercial hub: scale-out, managed offering and paid enterprise tier (effort XL)

**Thesis.** A single-maintainer Apache-2.0 project has a sustainability problem that procurement will notice, and free orchestrators have a weak commercial record. Make the commercial path explicit: keep the core permissive and sell the enterprise tier (SSO/SCIM, multi-team, HA, support), possibly as a managed hub. This is a company-building bet.

**What it means.** Decide on a split between the open core and a licensed enterprise add-on (SSO/SCIM, multi-team isolation, audit export, policy engine), as OpenHands and Coder do. Add a storage seam and an optional Postgres backend for failover and multi-node hubs, but only against a named customer requirement (consistent with D37), and measure the single-connection SQLite hub under realistic UI and SSE load first. Add scheduled backup to object storage (Litestream sidecar) with a stated RPO and RTO and an upgrade and rollback runbook. Consider a managed hub service (links still outbound-only, code never leaves customer machines), a support subscription and a certified installer. Seek a second maintainer or sponsor, and resolve the EU Cyber Resilience Act manufacturer versus steward question with legal advice before selling anything.

**Enterprise value.** Answers the 'who supports this' and 'what if the maintainer leaves' questions that decide enterprise purchases, and funds the hardening work in D2 and D3. HA and managed hosting would meet customers that need stated recovery objectives.

**Main risk.** It shifts a single maintainer into running a company against VC-funded rivals (Factory, Cursor, Cognition) and platform owners that can absorb features quickly. Licence changes can alienate users and invite forks (Apache-2.0 is permissive). A managed hub sits uneasily with the 'hub in your hands' pitch and brings CRA and data-handling obligations. Postgres adds a second storage path to test. There is no evidence yet that anyone would pay.

## The committee

### CISO / security architect at a regulated enterprise deciding whether a team may run coding...

Handloom's control model is better than most of the market: people-only approval, device-run checks, hash-pinned profiles, a hub with no shell, and honest "what it cannot enforce" docs. But I would not approve it on a production-adjacent machine today, for three reasons that all come from its own docs. (1) Agents run as the link's OS user with unattended flags and nothing separates them from that user's files (docs/isolation.md says container mode is "designed, not built"). (2) The device trusts the hub for everything. Profiles and the job's verify command are hub-supplied, and D56 and D61 defer per-device approval. A compromised hub, or anyone who can post to it (the README says this in so many words), can choose what an agent may do and run a shell command on every linked device. The blast radius of one hub credential is the whole fleet. (3) Every signed-in person sees every job, and the audit log is neither chained nor exportable. The biggest issue is (2) combined with (1): it is a single point of trust with no isolation underneath it. Device-side approval of profile and verify-command hashes is cheap and is the best security return per hour on the list, yet it sits buried inside D2. Features that widen exposure (D4 triggers with inbound webhooks, D7 remote MCP, D10 business workflows) should come after the containment and identity work, not before. The research is thin on what security reviewers actually ask for. The "SSO is a blocker" evidence is low-confidence, and the docs that matter come from vendors and secondary blogs. I would still bet that isolation and a hub that is not a fleet-wide RCE are the real gates, and SSO is the second gate.

**Top bets:** D2, D5, D3, D1

**Stop or avoid:**

- Do not ship inbound webhooks, event triggers or remote MCP (D4 and D7 phase 2) before container isolation, device-side profile and verify-command approval, and team scoping exist.

- Do not describe the product as compliant, certified or safe; use 'supports controls for', with the enforced / instructed / not-built table.

- Do not build a workflow engine or journaled replay (D1 should stay at fencing, idempotency and handoff notes).

**Enterprise must-haves:**

From a security view they widen the attack surface of a system whose containment is not built. I also expect them to treat D1's correctness work as the safe do-less choice. ### Platform and SRE lead who has run durable workflow systems in production: what breaks at 3...

Handloom's architecture suits an operator: one SQLite file, an outbound-only link, git as the unit of durability, a hub with no shell, and a person-only gate. That is boring in a good way. I read DECISIONS.md. Backup is VACUUM INTO, restore checks integrity, and the hub snapshots before migrations (D38). That is a real start. But the recovery story is a set of implementation facts, not a contract. Nobody can answer these today: (1) What happens to a running job when the hub restarts or is restored from a backup older than the link's state? (2) What happens when a link reconnects after a partition and its agent submits against a lease the hub already expired and reassigned? There is no fencing, so the answer is probably "last write wins". (3) What is the RPO? Backups are manual, so it is unbounded. (4) What do you page on? Agents with no terminal never expire (D53). A stuck agent that claimed nothing is invisible (F1). Time, turns and cost are not enforced (D56). (5) What does upgrading the hub or link do to in-flight work? D95 says it is untried. (6) The hub is a single point of failure for the gate, and there is no stated degrade mode. The biggest issue is that the project is about to add unattended triggers, a public inbound endpoint and more teams on top of a core that has no stated invariants under crash, retry or partition. Fix the core contract first. Then add the flight recorder and operational surface (metrics, export, backup schedule, runbooks), then isolation, and only then schedules. The competitive and standards tracks are noise from where I sit. Nobody pages on an A2A card. Vendor durability claims are weak too: Claude Code's resume is a prompt-level "check whether it took effect", not a guarantee. A hub-enforced guarantee is a real, cheap, defensible edge.

### Applied AI researcher on agent reliability and evaluation: what makes multi-agent coding s...

Handloom's architecture is the shape the better evidence favours: a centralised lead, a device-run check, human acceptance, and state in git and files. That evidence is thin and mostly not about coding. The Google 17.2x vs 4.4x result used non-coding tasks. MAST describes failure taxonomies, not what to do about them. The Anthropic and Cursor posts are single-vendor accounts. The durability preprint is single-author and un-replicated. Handloom's own proof is 3 to 5 runs per scenario, nearly all small jobs where one task and one worker is the right plan (D63, D65, D73). Three claims are unmeasured: "the lead plans well", "the check gates quality" and "the human gate works". The biggest problem is that the product's central guarantee, evidence-gated acceptance, is only as strong as the check command and the attention of the person accepting. Neither is measured. Nothing tests whether the check can tell a wrong solution from a right one. Nothing tracks how often a person rubber-stamps. Nothing records how often a lead mis-decomposes a job with dependencies. The committee is about to spend a year on enterprise plumbing (SSO, isolation, triggers) on top of unmeasured core reliability. Triggers and unattended runs multiply every undetected failure mode. My direction is to instrument and measure first. Treat fencing and idempotency as cheap hygiene, not as the reliability story, because Handloom's side effects are mostly git, which is recoverable. The real killers are silent stuck agents, runaway loops, weak checks, mis-planning and reviewer fatigue.

**Top bets:** D9, D1, D5, D2

**Stop or avoid:**

- Do not ship triggers, schedules or any unattended mode (D4) before per-task enforced budgets, stuck/no-progress detection and outcome metrics exist. Automation multiplies unmeasured failure rates.

### Red-team skeptic: argue Handloom should not exist, or should be much smaller. What is hype...

Handloom's real value is one narrow idea: a hub that holds no code, shell or model, plus a device-run check and a human-only accept, across several agent CLIs and local models. Everything else in the candidate list is either a catch-up race or a bet on a buyer nobody has shown exists. Five facts decide my view. (1) The research found no first-hand evidence of team demand for a cross-vendor coordination layer; every demand claim is vendor roadmap or analyst framing. (2) Local worktree-plus-tmux orchestration is commoditized: Claude Code agent view, Cursor, Conductor, Gas Town and Emdash all do it, and Vibe Kanban shut down because free orchestration has no business model. (3) The closest real competitors, OpenHands and Coder, are funded, already have SSO, RBAC, isolation and air-gap, and Anthropic, Cursor and GitHub each ship governed or self-hosted execution. (4) The headline enterprise features (SSO/SCIM, team isolation, container isolation, triggers, remote OAuth MCP, Postgres, a managed service) are each months of work for one person, and shipping any of them half-finished is worse than saying 'not built'. (5) Several arguments in the evidence are weaker than they look: the correctness case rests on one unreplicated single-author preprint about LangGraph and CrewAI, not about git-and-lease systems; the 'unoccupied ground' claim is inferred from absence in pages the researchers happened to open; the 'durable' framing overlaps with what vendor CLIs now do themselves. The biggest issue is that the committee will be tempted to turn a good personal tool into a procurement-checklist chase it cannot win. My recommendation is a much smaller project: be the best at the gate (evidence, device check, human accept, local-only confidential jobs), harden that gate, build only the one isolation mode that makes unattended use defensible, and stop there. Anything that needs a second maintainer to be honest (SSO plus team scoping, triggers, Postgres, business workflows, a company) should be cut until a paying or piloting user asks for it by name. Biggest single risk: building enterprise surface area before a single external team has used the product.

## Research by track

### Durable execution and long-running agent harnesses

The field has split the problem in two. General durable-execution engines (Temporal, Restate, Inngest, DBOS, LangGraph checkpointers) make the agent loop itself replayable by journaling every LLM and tool call, and they treat a human approval as a suspended state that costs nothing while it waits. Coding-agent harnesses (Anthropic, Cursor, Ralph-style loops) take another route: each context window is disposable, and durable state lives in files, git history and task lists that a fresh session re-reads. Handloom's design (task graph and evidence in the hub, work in git worktrees, leases, a person-only approval gate, a replaceable lead via job resume) is already on the second path and matches Anthropic's published guidance. Anthropic's April 2026 Managed Agents design goes further: session event log, stateless harness and sandbox are separate replaceable parts, and wake(sessionId) restarts a crashed harness from the log. Claude Code now ships its own local supervisor (agent view) and cloud Routines, so a durable background session on one machine is becoming a vendor feature rather than a differentiator. The strongest new evidence is about correctness. An August 2026 conformance study (arXiv 2608.03836) finds at-least-once effects across crashes in LangGraph, and a parked interrupt resumed concurrently by k processes fires its effect k times. ACRFence (arXiv 2603.20625) shows that retrying an LLM tool call after restore can duplicate a side effect because the model regenerates a different request. For Handloom the gaps are guarantees (fencing, consume-once answers, idempotent effects, a replayable run log, a handoff artifact convention, schedules and triggers, version pinning of in-flight jobs), not adopting a workflow engine.

**Implications for Handloom:**

- Position Handloom as the coordination and control layer around coding agents that already have their own session persistence. Do not build a Temporal-style journal for the agent loop. The unit of durability should stay the task graph, git branch and device-run evidence. This matches Anthropic's artifact-based guidance and Cursor's practice, and the vendor CLIs are absorbing per-session durability (agent view, Routines).
- Define and ship a handoff artifact convention: a required progress or handoff note per task (state, what was tried, next step, how to verify) that the hub stores, the link writes into the worktree, and a replacement agent is told to read first. The Anthropic initializer/coder split maps to lead-plans and worker-executes, but Handloom has no equivalent of claude-progress.txt or the JSON feature list with pass/fail.
- Add correctness guarantees that the survey shows even mature frameworks lack: a fencing token or epoch on leases, so a lease-expired or reassigned agent cannot submit or accept; idempotency keys on submit, accept and answer; and consume-once semantics for answering an escalation. This is cheap with one SQLite writer and would be a real differentiator against LangGraph and CrewAI, which fail concurrent-resume tests.
- Make the resume policy explicit and mirror Claude Code's rule: never silently re-run a tool call that was cut off, tell the resumed agent it was interrupted and require it to verify state (git status, task state) before acting. Document which effects Handloom can and cannot make safe, since git is recoverable and external APIs are not (ACRFence).
- Add an append-only per-run event log (spawn, wake, lease, tool-call summaries, submits, checks) as a first-class, exportable record. It serves the enterprise audit story that Temporal is selling ('every input, every decision, every tool call') and gives post-incident replay without a durable-execution engine. The existing audit log is a base.
- Treat human-in-the-loop as an explicit state machine, in the style of MCP Tasks' input_required and Inngest's waitForEvent with timeout: question timeouts, reminders and escalation to a second person, delegation, and per-team routing. This ties to issue #13 (per-person alerts and isolation) and to enterprise approval workflows.
- Schedules and event triggers (issue #6) are the largest functional gap against Routines, Inngest and Temporal. Build them as job templates plus a trigger table in the hub (cron, webhook, GitHub event) with idempotent firing, so a missed or duplicated trigger cannot start two jobs.
- Add a fresh-start and budget policy: recycle long-lived leads and workers after a time, token or turn limit with a forced handoff note; give per-task budgets; and give a stuck or give-up exit. The F1 hole (a stuck agent that claimed nothing is invisible) and the Ralph failure mode are the same problem.
- Plan for in-flight upgrades. Temporal's GA Worker Versioning and Restate's immutable deployment URLs show enterprises will ask what happens to running work when code changes. Profiles are hash-pinned, which is a good start; state explicitly that a job keeps the profile version it started with and what happens when the link or hub binary is upgraded mid-job (D95 lists upgrade between releases as untested).
- If Handloom later exposes jobs to remote MCP clients (issue #4), model long jobs on MCP Tasks (working, input_required, terminal states, ttl, authorization binding) rather than inventing a vocabulary.

**Risks:**

- Overclaiming durability. 'Durable' to an enterprise buyer means a crash does not lose or duplicate work. Handloom today offers lease-based detection plus recovery by git and a replaceable lead, which is weaker than journaled replay. Wording in docs and marketing should say what survives (task graph, committed branches, evidence) and what does not (uncommitted worktree changes, agent context, non-git side effects).
- Commoditisation. Claude Code's agent view, Routines and Managed Agents, and equivalents from OpenAI and Cursor, give a single vendor's agents durability and scheduling. Handloom's cross-CLI, self-hosted, local-model and person-approval angle is real, but it must lead with multi-vendor, multi-machine, audit and confidentiality rather than keeping an agent alive.
- Scope creep toward a workflow engine. Temporal, Restate, DBOS and Inngest are well funded and mature. Re-implementing journaling or replay in a single-maintainer project would be a trap. Integration points are safer than reimplementation.
- Semantic rollback: a headless wake or resume can repeat a side effect with changed parameters (ACRFence). Handloom's deny lists and the link-side merge reduce this for git but not for MCP tools or APIs an agent calls.
- The agent-view 48-hour window, session retention (30-day default) and CLI version drift mean Handloom's headless resume depends on vendor session behaviour that changes between releases and is undocumented as a contract.
- Single maintainer: any added guarantee (fencing, event log, triggers) needs tests and a fault-injection suite like m0 to m2 and b.sh, or it becomes untested code that D51 already warns against.

### Agent harness design and the agent-CLI ecosystem

As of 2026-10-09 the coding-agent harness has converged on a recognisable shape: a hand-rolled agent loop, SKILL.md skills, MCP tools, markdown subagent definitions, lifecycle hooks, plan/permission modes and project-instruction files. An academic source-code study of 11 harnesses found SKILL.md in 9 and MCP in 8. The formats sit under neutral governance (AGENTS.md, MCP and goose at the Linux Foundation's AAIF since 2025-12-09; Agent Skills as an open spec; ACP for editor-to-agent). Convergence is not interchangeability: Claude Code reads AGENTS.md only when no CLAUDE.md exists, and multi-agent topology differs (peer-messaging teams, path-addressed subagents, @-named subagents, recipes). The big 2026 shift is that every major vendor now ships its own multi-session and multi-machine control layer, and each is single-vendor: Claude Code agent view (local-only) plus cloud sessions and Managed Agents; Cursor Agents Window, self-hosted machines (2026-09-02) and Projects (2026-09-10); GitHub Agent HQ with an Agent Control Plane that hosts Claude and Codex (2026-02-26); Codex app-server, hooks, access tokens and event-triggered tasks. Local worktree-plus-tmux orchestration is therefore commoditized, schedules and triggers are table stakes, and per-vendor governance (managed settings, OTel, audit logs) is growing. What remains open for a layer like Handloom is vendor neutrality across CLIs and models (including local models), device-verified evidence, human-only approval and self-hosting. Two caveats: I found no direct evidence of team demand for a cross-vendor layer, and many sources are secondary summaries (flagged per finding).

### Enterprise governance, identity, security and compliance for agents

As of 2026-10-09 there is still no binding, agent-specific certification regime. What exists is a fast-converging stack of guidance and products. OWASP published its Top 10 for Agentic Applications on 2025-12-09. NIST has only drafts (the NCCoE agent identity concept paper of 2026-02-05, the CAISI initiative of 2026-02-17, the Cyber AI Profile draft IR 8596, and COSAiS SP 800-53 agent overlays not expected before late 2026 or 2027). Singapore's IMDA agentic framework (2026-01-22, v1.5 2026-05-20) is voluntary. The EU AI Act high-risk dates moved to 2027-12-02 (Annex III) and 2028-08-02 (Annex I) under the Digital Omnibus, which entered into force in late July 2026; most enterprise coding-agent use is probably not high-risk, but that is my inference, not checked against a primary legal source. Enterprise expectations are concrete in practice: a unique, scoped identity per agent, delegation traceable to a named person, human approval of sensitive actions, tamper-resistant logs and an agent inventory. Auditors for SOC 2 and ISO 42001 certify the organisation, not the tool, so a self-hosted open-source harness can supply evidence and enforcement points but not a certificate. Prompt injection is not solved: adaptive attacks beat 12 published defenses at over 90 percent. The accepted answer is architectural, meaning least agency, OS-level sandboxing, human gates and Meta's Rule of Two. Handloom's existing design (people-only approval, device-side checks, hash-pinned profiles, scoped tokens, local-only confidential work) lines up well with this direction. Its main gaps are those a security reviewer would flag first: no OIDC/SSO or workload identity, no isolation beyond the OS user, an audit log that is append-only by trigger but neither chained nor signed, no per-team isolation, no separation of duties between starter and approver, and a hub whose compromise controls what agents may do on every device.

### Interoperability standards and protocols

As of 2026-10-09 the standards picture has consolidated. MCP is the de facto tool and context protocol: its 2026-07-28 revision (final 28 July 2026, RC 29 May) is the biggest breaking change since launch. It removes the initialize handshake and Mcp-Session-Id, adds a mandatory server/discover, replaces server-initiated requests with multi-round-trip requests, and moves Tasks into an official extension. It also deprecates Roots, Sampling, Logging, HTTP+SSE and Dynamic Client Registration. Its authorization model is OAuth 2.1 with RFC 9728 protected-resource metadata, RFC 8707 resource indicators, RFC 9207 issuer checks and Client ID Metadata Documents; enterprise-managed authorization (ID-JAG) is an official extension. AGENTS.md (60k+ projects claimed) and Agent Skills (SKILL.md, supported by Claude Code, Codex, OpenCode, Pi and dozens more) are the settled formats for agent instructions. **Implications for Handloom:**

- Handloom's MCP server (D29: about 300 lines written by hand, newline-delimited stdio JSON-RPC speaking initialize, ping, tools/list, tools/call) predates the 2026-07-28 revision. New SDKs stop sending initialize, so it needs server/discover, per-request _meta version handling, resultType on results and the new error codes. Dual-mode support is allowed by the spec's backward-compatibility rules. I could not verify how Claude Code, Codex, OpenCode, OMP and Pi fall back against old stdio servers, so test each against both modes before releasing.
- Remote MCP on the hub (D78 lists it as 'not built, needs OAuth') should follow the 2026 recipe: publish RFC 9728 protected-resource metadata, act as or delegate to an authorization server with RFC 8414 metadata, accept CIMD client IDs, enforce RFC 8707 audience-bound tokens, and return 403 insufficient_scope for step-up. The existing split holds: tokens limited to read and start, with approval reserved for signed-in people. Use CIMD, not DCR, which is deprecated.
- For enterprise and teams, the standards path to SSO/SCIM and per-team isolation is the Enterprise-Managed Authorization extension (ID-JAG). The hub could be the MCP authorization server that validates an enterprise IdP's ID-JAG. Client support is thin or unverified outside Anthropic's products, so this is a design-for item for 2027, not a launch blocker; OIDC login for people is the nearer step.
- MCP Tasks (durable task handle, input_required, tasks/update) is a close conceptual fit for a remote Handloom operator surface: start a job, poll, and surface an agent's question while keeping the answer a human-only action. Align the vocabulary (working, input_required, completed, failed, cancelled) rather than adopting the extension early.
- Observability: do not make the OTel GenAI conventions a hard dependency. Adopt W3C trace context (a job's trace id passed to agents through TRACEPARENT, and in MCP _meta) and export hub and link spans through OTLP under a Handloom-owned namespace, with an opt-in mapping to gen_ai.* attributes. Claude Code already honours inbound TRACEPARENT in -p sessions and propagates it to subprocesses and HTTP MCP, so cross-agent traces are feasible today. Keep Handloom's internal metrics model independent of the unstable external schema.
- Instructions and skills: Handloom profiles already carry skills and prompts. Align them to SKILL.md folders and AGENTS.md rather than inventing formats, and re-test the Codex 'skills not verified' note in D58 against the agentskills.io listing.
- A2A: watch, do not build now. The case for it is cross-system calls to foreign agent platforms, which no Handloom user has asked for in the evidence here. The adoption evidence for coding agents is thin and the first security analysis found spec-level issues. If a customer needs it, an A2A Agent Card plus task endpoint in front of the hub's start-job and status calls would be a thin adapter, because A2A's task states resemble Handloom's job states.
- AAIF neutrality (MCP, A2A, AGENTS.md under one roof) reduces standards-capture risk and supports an 'implement open standards, stay vendor-neutral' pitch for enterprises. It also means roadmap decisions run through a foundation board and technical committee dominated by large vendors, so a single-maintainer project should track SEPs rather than expect to shape them.

**Risks:**

- Stdio compatibility cliff: SDKs updated for 2026-07-28 no longer send initialize. If an agent CLI updates before Handloom's MCP server does, agents could silently lose their handloom tools. The whole coordination loop (inbox, submit) runs over MCP for Codex, so this is high impact. How each CLI falls back is unverified.
- Standards churn: MCP is now a rapid-revision protocol (2025-11-25 then 2026-07-28 within eight months), with deprecations on a 12-month minimum clock. A solo maintainer must budget recurring spec-tracking work.
- OTel GenAI conventions are pre-stable with renames already shipped, so binding Handloom's data model to them could force breaking changes in stored metrics and exports.
- Enterprise-managed authorization is built on an IETF draft (ID-JAG) with one reported IdP (Okta) and uncertain client support, so investing early may not pay off.
- Remote MCP and OAuth substantially widen Handloom's attack surface: it is the first inbound public endpoint, and the claimed advantage of 'outbound-only link, hub with no shell' still holds, but the hub becomes an authorization server or must trust an external one. Per-team isolation is also still missing, so a remote token would expose every job to any signed-in person.
- MCP security incidents (tool poisoning, auto-executed project MCP servers) are widely reported but only from secondary sources here; enterprise buyers will ask how profiles restrict MCP servers per agent.
- Secondary-source dating conflicts (A2A joining AAIF is reported as 17, 20 or 27 August 2026), so any dated claim in a public document should cite the primary page.

### Competitive and adjacent landscape for team agent orchestration

As of 2026-10-09 the market has split in three. (1) Vendor-run background agents (Devin, Cursor, Copilot coding agent and Agent HQ, Codex cloud, Claude Code on the web with routines, Jules, Factory, Amp, Warp Oz) are heavily funded and moving fast on schedules, event triggers, isolated VMs and enterprise controls. (2) Local single-developer orchestrators (Conductor, Claude Squad, Emdash, Gas Town, an Agent Orchestrator, Vibe Kanban) are plentiful and cheap. (3) A small group of genuinely self-hosted team platforms (OpenHands Enterprise, Coder Agents/Coder AI governance) is the real competitive set for Handloom. The key structural fact is that every vendor "self-hosted" mode (Cursor worker pools, Devin VPC, Claude Code self-hosted environments) moves only the execution body into the customer's network; planning, inference and the control plane stay in the vendor's cloud, and Claude Code's self-hosted mode is unavailable with Zero Data Retention or HIPAA. That leaves ground for a fully self-hosted, vendor-neutral control plane, but OpenHands (MIT core, about 90k stars, ACP, automations, RBAC/SAML, budgets) and Coder (air-gapped, any agent, firewall, AI gateway, SIEM export) already occupy the general version of it. The narrower unoccupied position is an evidence-gated, human-only-approval harness whose hub never runs git, a shell or a model, with per-client knowledge repos, aimed at small regulated and consultancy teams. Several earlier differentiators are eroding: multi-CLI support is common, and GitHub's Copilot CLI and app now offer BYOK plus Ollama/vLLM and an offline mode. Handloom is clearly weaker on SSO/SCIM, per-team isolation, container isolation, schedules and triggers, remote MCP/OAuth, case studies and maintainer count. Vibe Kanban's April 2026 shutdown, because its mostly free users gave it no business model, is a warning for free single-developer orchestration.

**Implications for Handloom:**

- Position Handloom's lead-plus-workers shape as the evidence-backed one. The Google result (4.4x vs 17.2x error amplification), Cursor's planner/worker/judge finding and MAST's emphasis on verification all favour a centralised lead with evidence-gated tasks and an on-device check. Make this visible: record, per job, how much work ran in parallel versus sequentially, and warn when a job's task graph is sequential but fanned out, since multi-agent variants lost 39-70% on sequential planning.
- Do not build a proprietary tracing format. Emit OTLP using the OTel GenAI span names (invoke_agent, execute_tool, chat) behind an adapter and pin the semconv version, because the conventions are still 'Development' and have just moved repos. Ingest or pass through native CLI telemetry (Claude Code already emits metrics, events and beta traces) and tag everything with job_id, task_id, worker, profile name and hash, device and lead. Langfuse (MIT, OTLP endpoint, self-hostable) is a natural reference sink for a self-hosted tool.
- Make the audit log a flight recorder, not just an event list. Per task, keep the full agent transcript or trace, the diff, the path-policy decision, the check command output, the accept or reject decision and who made it. Chain or sign entries so they can be verified and offer export. This follows the 'share full traces' lesson (Cognition), the resumable-checkpoint and full-tracing lessons (Anthropic) and tamper-evidence practice. It does not depend on any legal deadline, because the EU high-risk logging duties are now 2027-12-02.
- Add enforced budgets at job and task level, not just reporting. The state of the art is in-path, run-scoped STEER and HALT policies, whereas Handloom today has owner-entered prices and a command center. Candidates: a per-job token or cost ceiling, a max-iterations and wall-time limit per task, loop and no-progress detection (MAST's step repetition, 15.7% in one summary), and a circuit breaker that pauses a lead when workers repeatedly fail the check. Add cost per accepted task alongside raw spend, and design fields so they can map to FOCUS-style tags (team, client, cost centre) once the Tokenomics work lands.
- Default metrics for enterprise trust, all derivable from data the hub already holds: accepted-task rate, first-pass check success, rework or rejection rate, check-failure and merge-conflict rate, time to accept, human-wait time, cost per accepted task, policy-denial counts (denied commands and out-of-path submits), duplicate or abandoned task rate, agent question rate, and pass^k for a profile on a fixed benchmark task. The agentic-PR study's failure mix (abandonment, duplicates, CI failures) shows which of these matter. Leave SLO thresholds to the operator, as no validated standard exists.
- Ship an eval-from-history loop that avoids public benchmarks. Because SWE-bench Verified lost credibility in 2026, let teams replay a saved task or job against a new profile version or a new model and compare outcomes using repeated trials, clean worktrees and deterministic check commands (Anthropic's guidance). Tie profile hash-pinning to eval results, so a profile change can be gated on a regression suite in CI. That is a strong differentiator for 'durable' enterprise automation.
- Lean into the enforcement-not-prompts message. The April 2026 database deletion was an over-privileged credential plus prompt-only guardrails, and Handloom's denied commands, write-path allowlists, device-side checks and human-only acceptance are precisely the controls post-mortems recommend. Strengthen by also surfacing secrets exposed to agents, scoped credentials per profile, and the container isolation seam already designed (issue open).

**Risks:**

- OTel GenAI conventions may change again before stabilisation (the repo moved in June 2026 and has no release), so any attribute-level promise to customers could break. Pin versions and keep the mapping layer thin.
- Over-instrumentation raises privacy and confidentiality risk. Full transcripts and tool content can include client secrets and code, and 'confidential jobs on local models' means traces must stay local with redaction by default (Claude Code redacts by default for this reason). Also note that hub-side retention of transcripts expands what a hub compromise exposes.
- Budget enforcement can cause its own failures, such as halting a nearly finished task or steering to a weaker model that degrades quality. TokenOps' headline gains are vendor-reported on its own benchmark and not independently reproduced.
- Metrics invite Goodhart effects: optimising accepted-task rate or low cost per task can push agents toward small, safe changes (Cursor saw risk-aversion under flat coordination) or weaker tests. Pair outcome metrics with sampled human review.
- Evidence quality: many 2026 sources are secondary blogs, vendor-authored comparisons or LLM-generated summaries of primary sources. Several items (SLO targets, vendor rankings, agent merge rates, benchmark audits) are unstable, so avoid quoting them as facts in Handloom marketing.
- Single-maintainer capacity: a full tracing, eval and replay stack could exceed what one maintainer can support. Integration with existing OTel and eval tools is cheaper than building them.
- Over-parallelisation is still a risk Handloom does not control. Lead agents can fan out many workers on tightly coupled or sequential work, which the Google study shows reduces performance by 39-70% and which Cognition's 'conflicting implicit decisions' argument predicts.

### Automation, triggers and enterprise workflows for agents

By October 2026 every major coding-agent vendor ships the same three-part automation surface: a schedule, an HTTP or webhook trigger, and source-control or issue events. Claude Code Routines (research preview), Cursor Automations (March 5, 2026), Codex automations and GitHub Agentic Workflows (technical preview, February 13, 2026) all do this. The shapes with real evidence of durability are narrow and verifiable: scheduled chores and triage (docs drift, backlog grooming, CI-failure summaries), PR review and security scans on events, alert-to-draft-PR, and large codemod or migration fleets. Stripe reports over 1,000 merged agent PRs a week and Spotify reports over 1,500 merged PRs, with about half of its PRs automated by Fleet Management. In all of these a human reviews and merges, and the agent runs in an isolated environment with deterministic steps and a hard cap on CI retries. Incident-response agents (AWS DevOps Agent, GA 2026) investigate and propose, and a person approves mitigation. The control vocabulary has also converged: read-only by default, typed capped write channels ("safe outputs"), per-run and per-day credit caps, a staged or dry-run mode, per-user rate limits, hourly trigger caps, and an owner-level disable switch. The main documented hazard is untrusted trigger content: issue and PR text in prompts led to secret exfiltration in "PromptPwnd" (disclosed December 2025). The data on agent PRs shows a review-capacity problem: in the 33,596-PR AIDev subset, 38% of rejected PRs were abandoned with no human interaction and 23% were duplicates. Money is flowing into durable workflow engines (Temporal $550M Series E at $12.55B, September 2026; Restate $20M Series A, September 30, 2026), but I found no evidence that organisations drive coding-agent CLIs through them in volume; that use is mostly API-level agents. Identity vendors are moving to per-agent identities with a named human sponsor (Microsoft Entra Agent ID). Handloom's differentiators (self-hosted, per-device checks, only people approve, local models) fit the safe-automation pattern. It lacks the trigger layer and enforced budgets that its competitors now treat as standard.

**Implications for Handloom:**

- Schedules and triggers are now table stakes. Build a minimal, safe trigger layer: cron schedules, a signed inbound webhook and a per-automation token, plus optional GitHub/issue events. Keep it small and use the same primitives for all of them: a 'trigger' creates a job from a saved template (profile, brief, repo, check command).
- Make the trigger fire a job, never act directly. Handloom already has the right backbone: a job produces tasks with evidence, and the device runs the check and path allow-list before a person accepts. Do not add a 'run unattended and auto-merge' mode. The review queue is the product; Stripe, Spotify, AWS and the AIDev data all end at human review.
- Safety envelope per automation, enforced in the link and hub rather than by prompt: (1) hard caps per run (wall time, agent turns, tokens or owner-entered cost) and per automation per day, stopping at the cap; (2) max concurrent and max queued runs per automation, with a skip-if-previous-run-open and 'skip if an open job exists for this key' option; (3) idempotency keys on webhooks and a dedupe window, because 23% of rejected agent PRs were duplicates; (4) consecutive-failure circuit breaker that pauses the automation and alerts; (5) kill switch at three levels (one automation, all automations, hub-wide) that also cancels running jobs; (6) a staged or dry-run mode that creates the job record but starts no agent; (7) an audit entry for every fire, skip and cap hit.
- Treat trigger payloads as untrusted data. Store the payload with the job, pass it to the lead as a clearly delimited data block, and let the saved template decide whether to act on it (as Claude Routines do). Restrict triggered jobs to least-privilege profiles (read plus propose, no network or secrets by default), and prefer propose-on-branch outputs like the knowledge-note flow. Never let issue or alert text choose the profile, device or check command.
- Give each automation a named human owner and its own identity (token, audit name), echoing Entra's 'sponsor' concept, and show owner, last fired, next due, spend and open runs in the command center. Vendor routines run as the creator's identity and belong to one account, so a team-owned, auditable schedule is a real gap that Handloom can fill. Fix the per-team isolation gap (issue list) before offering team-owned automations to enterprises.
- Start with the automation shapes that have evidence: scheduled chores that end in a reviewable artifact (docs drift, dependency or backlog triage, CI-failure summaries), PR review on event, alert-to-draft-PR with the alert as untrusted text, and migration fleets that fan out many small identical jobs. The knowledge-repository 'librarian' (D68, deferred because it needs schedules) is a good first schedule: low-risk, proposes on a branch and a person merges.
- Self-hosting plus local models is a defensible niche against hosted routines, especially for confidential work. Hosted vendors now offer self-hosted environments for routines, so lead with what they do not offer: multi-vendor agent CLIs, per-device checks and path enforcement, a human-only accept rule and local-model confidential jobs.
- Do not build or embed a general durable workflow engine. Borrow its semantics instead: the hub's level-triggered state, leases and the link's retry ladder already give resume after a crash. Document the integration route (an external Temporal or n8n flow calling the hub's operator API or MCP to start jobs and wait for human approval) rather than implementing one.
- Consider shipping enforcement of time and turn limits before schedules. D56 says time, turns and cost are not enforced, which becomes unacceptable once nobody is watching. Cost needs owner-entered prices (already in the command center), so a per-automation daily cap is feasible.

**Risks:**

- Hosted vendors (Anthropic Routines, Cursor, Codex, GitHub) are shipping triggers and review queues fast and bundling them with the model subscription; a single maintainer cannot match their pace of features and integrations, so Handloom must win on control, self-hosting and multi-vendor, not breadth.
- A trigger layer turns a human-in-the-loop tool into one that spends money and touches repos at 3am. One runaway automation, a prompt-injection through a webhook payload, or a duplicate flood would damage trust in a pre-1.0 project that has no published case studies.
- Per-team isolation is missing: with schedules and shared triggers, every signed-in person sees every job and automation, which blocks enterprise use where teams must not see each other's work.
- Review capacity is the real bottleneck: if schedules multiply jobs, the inbox fills and PRs go unreviewed (38% of rejected agent PRs were abandoned). The risk is that the feature increases noise, not value.
- Outbound-only link design is safe, but inbound webhooks require a public hub endpoint, signature verification, replay protection and rate limiting. That widens the attack surface of a hub that deliberately had no shell or model in it.
- Standards are moving: MCP Tasks and enterprise-managed authorization (2026-07-28) and remote MCP/OAuth could change how AI apps integrate. Building a bespoke trigger API now may need rework.
- Evidence for non-coding enterprise automation (back office, knowledge work) is thin in this research. Positioning Handloom's 41 non-engineering starter profiles around scheduled business workflows is unproven.

**Gaps (not found or not verified):**

- Found no primary adoption numbers for Claude Routines, Cursor Automations, Codex automations or GitHub Agentic Workflows beyond launch posts and docs; 'durable versus demo' is judged from the shape of the controls and the few disclosed production cases (Stripe, Spotify), not from usage data.
- Did not research back-office and knowledge-work automation (ServiceNow, Salesforce, UiPath, n8n, Zapier agents, finance or HR flows), so no evidence either way for the non-engineering side of Handloom's starter profiles.
- Incident-response outcome numbers (MTTR) are vendor-reported or from secondary summaries; I did not open the underlying SRE surveys (Dynatrace, NeuBird, SRE Report) or independent evaluations.
- Runaway-cost incidents come from blogs and issue threads; no primary postmortem was opened. Cost figures should be treated as anecdotes.
- Did not open the Temporal Series E primary announcement, the Temporal OpenAI Agents SDK GA page, or the MCP August 2026 roadmap post; those claims rest on press or search summaries. The AWS DevOps Agent GA date (March 31 versus the June 18 blog) is unresolved.

### Isolation, deployment and enterprise operability

As of 2026-10-09, per-agent isolation, controlled egress and secrets injected by a proxy outside the sandbox are the baseline for any platform that lets coding agents run unattended. Docker launched local microVM Sandboxes (sbx) in March 2026 and Cloud Sandboxes on 2026-09-24. Claude Code's docs say unattended runs belong inside a container, VM or sandbox runtime. Kubernetes now has an upstream Agent Sandbox project (gVisor or Kata via RuntimeClass). Handloom's link starts agents on the host as the link's user, with no separation from that user's files; docs/isolation.md says container mode is designed but not built. The competitive picture has changed in the last two months. Anthropic shipped self-hosted runners for Claude Code (beta, 2026-08-07) that use the same outbound-only pattern as Handloom's link, but the control plane and session content stay at Anthropic. Coder Agents went GA on 2026-09-09 as a fully self-hosted, air-gap-capable offering with RBAC and audit. OpenHands Enterprise sells SAML, RBAC, audit and sandboxes as a commercial tier. Handloom's real differentiators are a self-hosted control plane, a multi-vendor CLI mix, local-model confidential jobs and per-job human approval. The enterprise gate items it lacks are OIDC/SAML SSO, SCIM, per-team isolation, an SBOM, and container or microVM isolation. For the hub, SQLite in WAL mode on one node is defensible: the hub is a low-write coordination plane, and Handloom already has backup and restore plus pre-migration snapshots. It stops being enough when a customer needs failover or a stated recovery point and time, or more than one hub node. SQLite WAL cannot span hosts, and Litestream is asynchronous backup, not HA. I found no source that gives a write-throughput threshold for hubs like this, so the "where it stops" answer is based on capability limits and not on measured load.

**Implications for Handloom:**

- Minimum credible baseline today, in priority order. (1) Build the container isolator behind the existing Isolator seam, OCI-runtime-agnostic (runc hardened by default; runsc or kata selectable), with default-deny network, a per-profile egress allowlist via a proxy, no Docker socket, and credentials held outside the box. (2) OIDC SSO, with SAML only if buyers demand it, plus group-to-role mapping; add SCIM later. (3) Per-team scoping of jobs, machines and alert topics inside one hub (issue #13). (4) Audit export (syslog or webhook or file) and retention settings. (5) Documented backup schedule with stated RPO/RTO, plus an upgrade and rollback runbook. (6) SBOM and govulncheck in the release workflow. (7) An air-gapped install guide covering offline binary, container image, pre-staged model weights and an internal git remote.
- Lead with the self-hosted control plane as the position. Anthropic's runners and Coder Agents show buyers want agents executing inside their network; Handloom's distinction is that the hub, the audit log and the approval rules are also in their hands, across several agent CLIs, with confidential jobs on local models. Do not compete on sandbox technology; consume it (Docker sbx, Kata, gVisor, K8s Agent Sandbox) through the Isolator seam.
- Credential design should change before the container isolator is written. docs/isolation.md plans to seed each box with minimal CLI login files; the market pattern is a proxy that injects secrets so the box never holds them. At minimum, make that an explicit option for cloud-CLI profiles, and keep local-model profiles free of any cloud credential.
- Keep SQLite as the default and say plainly where it stops: one hub, one node, async backup, no failover. Add scheduled backup to object storage (a Litestream sidecar is the lowest-effort path) before any Postgres work. Treat a Postgres backend as a decision gated on a named customer requirement (failover, multi-node), consistent with D37, and measure the single-connection hub under realistic UI and SSE load first.
- A remote MCP endpoint should be an OAuth 2.1 resource server against MCP spec 2026-07-28, with scopes that encode 'read and start, never approve'; EMA support lets an enterprise IdP govern which AI apps may connect, which fits Handloom's operator-token model.
- Per-team isolation is the largest structural gap for enterprise use: every signed-in person sees every job, and a machine belongs to the hub. Until it exists, the honest enterprise answer is one hub per trust boundary, which the README already says.

**Risks:**

- Positioning risk: Anthropic, Coder and OpenHands are all moving into 'self-hosted agent execution' within the last two months; a single-maintainer project must pick the narrow ground (multi-CLI, local models, human-approval governance) and not chase their feature lists.
- Security-claim risk: shipping a 'container mode' that is a default Docker container with a bind-mounted repository and open network would be weaker than what vendors call adequate for unattended runs; the README and Claude Code docs both warn about this. Mounting the repository's .git read-write (isolation.md item 3) still lets a box damage history.
- Egress-control weakness: hostname-allowlist proxies can be bypassed with domain fronting unless TLS is inspected, per Anthropic's own docs; a Handloom allowlist feature should not be marketed as exfiltration prevention.
- Sandbox engine vulnerabilities and downstream patch lag are real (arXiv 2606.08433); Handloom should document which runtime versions it tested and not imply a security guarantee from the engine choice.
- Regulatory risk: CRA obligations (reporting live since 2026-09-11) depend on whether Handloom is treated as a manufacturer or a steward; this was not resolved and needs legal advice if any commercial offering is planned.
- Compliance gating: many enterprise buyers ask for SOC 2 and SSO before a pilot (low-confidence secondary evidence); an open-source project cannot produce SOC 2 itself, so the buyer's own controls and Handloom's documentation of what it does and does not enforce carry the review.
- SQLite single-writer and single-connection design is fine for the current target but unmeasured at team scale; an unexpected stall would surface as hub timeouts across all links.
