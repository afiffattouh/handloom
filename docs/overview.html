Handloom · hl · open source, self-hosted

One hub. Many devices. Agents that hand work to each other and show their proof.

You describe a job. A lead agent plans it and starts workers on your machines. Each worker gets its own copy of the repository. The device that holds the files checks the work, and only you decide it is finished.

hub: keeps the record, decides nothing device: the only place files and commands live you: the only one who approves
1 · Set up

From nothing to your first job

You need a server with Docker, a domain name, and one or more machines with git, tmux and a logged-in agent CLI. Four stages, each done once. After stage 1 you work in the web UI, and the inbox keeps a "Get started" checklist until all four are done.

The domain

Add a DNS A record (for example handloom.example.com) pointing at your server's IP and open ports 80 and 443. The included Caddy file then gets and renews the https certificate by itself.

The tokens

You handle almost none. A setup code (from the log, once) makes your owner account. A join command (copied from the Devices page) joins each machine. The admin token is an emergency key: save it, ignore it.

No domain?

On a private network (Tailscale, WireGuard, home LAN) skip it: use plain http at the private address with HANDLOOM_INSECURE=1. Never on the open internet.

Stage 1 · on a server

Run the hub

Once. Any VPS with Docker (Dokploy works too).

# DNS A record + ports 80/443 first
HANDLOOM_DOMAIN=hub.example.com \
docker compose -f docker-compose.caddy.yml up -d --build
docker compose -f docker-compose.caddy.yml \
  logs handloom | grep -E "setup code|Admin token"
  • Open /setup, enter the code, create your owner account
  • Keep the admin token safe
Stage 2 · on each machine

Join a machine

Once per machine: git, tmux and one logged-in agent CLI.

  • Put the handloom binary on it
  • Web UI: Devices, Add a device, copy the join command
handloom link join https://hub.example.com <token>
handloom link install   # starts at boot
handloom doctor         # what is missing?
Stage 3 · in the web UI

Make profiles

Once per kind of agent.

  • Profiles, Starter library: 41 starters, or New profile with guidance
  • One for a lead: usually read-only, plans and reviews
  • One or more for workers: the CLI, the tools allowed, the paths they may change
  • Or add ready-made ones from the starter library
  • Any CLI can fill either role
Stage 4 · in the web UI

Start a job

Every time you have work.

  • Jobs, New job: title and brief
  • Pick the device, the repository path and a check command
  • Pick the lead's profile
  • The lead starts workers. You answer questions and review
Get started checklist

The inbox lists what is left: join a machine, make a profile, start a job. Each line has a button to the right page, and the card disappears when all of it is done.

handloom doctor

Run it on a machine. It checks the link and hub connection, git, tmux, and each agent CLI (installed, logged in), and prints one fix per problem.

Prefer a script?

scripts/setup.sh device <ssh-name> --hub <url> builds the binary for that machine, copies it, and installs the link as a service.

2 · Topology

Where everything runs

The hub is one small container on a VPS. Devices only ever call out to it, so no machine needs an open port.

Agents never see the device credential

They talk to the link over a unix socket and prove who they are with a per-run token that is stored hashed on the hub.

Same CLI for you and for agents

The terminal, the web page and the MCP tools all call the same API, so every action leaves the same audit row.

Any agent CLI

Claude Code, Codex, OMP, Pi and OpenCode. The profile says which one and which model, and what the agent may do.

3 · Architecture

Who is responsible for what

The split is deliberate. The hub can be public and small because it never touches a repository. Everything that runs code lives on a device you own.

Hub

Records, routes, remembers

  • Jobs, tasks, dependencies, messages, escalations
  • Profiles stored as immutable versions with a hash
  • Spawn and merge requests as queue rows
  • Leases: an agent that goes quiet is marked offline, and a lost lead becomes an inbox item
  • Web sessions: argon2id, __Host- cookies, CSRF, step-up password for risky actions
  • Roles: owner, member, viewer

Rule: the hub stays dumb. It never runs git, a shell or a model.

Link on each device

Does the real work

  • Wake ladder: types a nudge into an idle agent's tmux pane
  • Spawn: git worktree, trust the folder, open a tmux window, run the agent CLI
  • Scope gate: refuses a submit that touched files outside the profile's globs
  • Verify: runs the job's check command on each submission
  • Merge: merges accepted branches into job/<id>/integration and re-checks
  • Vouch: tells the hub a pane still exists

Rule: the device's word beats the agent's word.

Agent

Plans or builds, then proves it

  • Runs inside one tmux window in its own worktree and branch
  • Sees only what its profile allows: tools, deny-listed commands, skills, prompt
  • Verbs: inbox, send, task create / claim / submit, ask, spawn
  • A lead plans and reviews; workers build
  • Submits with evidence (commit, file, test result)

Rule: only a human closes a job or answers an escalation.

5 · Guard rails

What keeps it honest

Only humans approve

Starting and closing a job, answering a question and changing profiles need a signed-in person. Agents cannot do any of them.

The device checks, not the agent

The check command runs on the machine that holds the files. Its exit code and output hash are stored next to the agent's own claim.

Scope is enforced at submit

Each profile lists the paths its agent may change. A submit that touches anything else is refused, and the refusal is logged. It fails closed.

Profiles are pinned

A spawn runs name@version with a hash. Editing a profile creates a new version; old rows cannot be changed.

Confidential stays local

A confidential job is only a flag plus an off switch on a public hub. It works because local-model profiles never leave your machines.

Everything is audited

Each action records who did it and how: run token, device-asserted or human session. Recent activity is on every job page.

6 · Teams

Working with other people

One hub serves one team. Everyone signs in to the same web UI, and everyone's machines can join it. The owner invites people and decides what each of them can touch.

Who can do what

Agents are not people: they can never start or close a job, answer a question or change a profile, whoever started them.

A day in a team

  1. Owner sets up the hub, joins the build machine, writes a "lead" and a "coder" profile, and invites two colleagues and the product manager.
  2. Member opens New job late in the afternoon: "Add CSV export to reports", build machine, the repo path, go test ./... as the check, lead profile. Then goes home.
  3. Lead plans three tasks and starts two coders. They work in their own copies. The build machine checks every submission.
  4. Lead asks "Should exports include archived reports?" It lands in everyone's inbox and the owner's phone.
  5. A second member answers it from the train. The first member's inbox now shows it as answered.
  6. Viewer opens the job page in the morning: three tasks done, each with its passing check, no questions open.
  7. First member reviews the work, closes the job, and merges job/<id>/integration into their own branch.

Ways to organise it

One team, one hub

The default. Everyone shares the inbox and the machines. Good for a team that trusts each other with the same repositories.

A separate hub per trust boundary

Only when a contract says client data must not share a system. Hubs share nothing, so nothing can leak across, but a machine joins one hub per Handloom home, so shared machines need extra setup. Most teams do not need this: separate clients by job, repository and knowledge repository.

Just you, several machines

The same product with one person: laptop, desktop and a server, one inbox on your phone.

What a team should know today

  • There is no per-person or per-team isolation inside one hub. Every signed-in person sees every job, and every member can start a job on any joined machine. The profile is the limit: it decides what the agent may do, and only the owner can write profiles.
  • A machine belongs to the hub, not to a person. Agents on a personal laptop use that laptop's own CLI logins.
  • There is one alert topic for the whole hub, not one per person.
  • The audit log records which person started, answered or closed things.
8 · Clients and knowledge

A shared record of each client, kept up to date by review

Each client gets one knowledge repository: markdown notes in git that link to each other with [[links]]. Agents read it before they work. What they learn comes back as a proposal, and only a person merges it. The hub never holds the notes, only a count.

you

1 · Keep a repository per client

Plain markdown in git, on a machine that joined the hub. Edit it by hand, in Obsidian, or both.

job

2 · Name it on the job

New job takes a knowledge repository path. Every agent in the job gets a checkout of it at .handloom/knowledge/.

device

3 · Agents read it

Lead and workers are told to read it first. Cloud models never get the confidential/ folder; local models do.

device

4 · Notes become proposals

Anything an agent adds there is gathered onto a branch job/<id> of the knowledge repository when work is accepted and when the job closes. The main branch is never touched.

you

5 · You merge what you accept

The job page counts the proposed notes and shows the two git commands to review and merge them. Nothing becomes "known" without a person.

later

6 · A librarian keeps it tidy

A scheduled job that finds stale, duplicate or contradicting notes and orphans, and proposes cleanups for review. Needs schedules.

acme-knowledge/                 # one repository per client, owned by you
  clients/acme.md                # "Invoice prefix: ACM. Billing contact: Dana. See [[contract-terms]]"
  decisions/2026-10-invoice-ids.md
  confidential/                  # local-model agents only; never checked out for a cloud model
    contract-terms.md
branch job/12                    # what job 12's agents proposed; you review it, then merge it
Continuing a project

A job points at an existing repository and starts from its latest commit. To build on unmerged work, give the job a base branch, such as job/12/integration. The repo's own CLAUDE.md / AGENTS.md comes along. The client's history lives in the knowledge repository, not in any one job.

One hub or several?

Default: one hub for the team, one repository and one knowledge repository per client. Split a client onto its own hub only when a contract demands it.

What the hub sees

The path of the knowledge repository and a count of proposed notes. Not the notes, not their file names. Backups of the hub do not contain client knowledge; back up the repositories with git.
