Help

How Handloom fits together and how to work with it day to day. Five minutes to read; the questions at the end cover what people usually get stuck on.

Order of thingsThe partsEvery dayTipsQuestions

The short version

Handloom lets you give work to coding helpers (AI agents that run in a terminal on one of your computers), then look at what they did before any of it is used. The helpers never change your project by themselves. A person reads the result, and a check that Handloom runs itself says whether it passes.

You ask for something, a helper does it on a copy, you see the files that changed and the check result, and you press Use this result or Send back with a note.

The order of things

The first time, once. Steps 1 to 3 are usually done by whoever runs the hub.

  1. Add a computer. On Computers, add the machine that will run helpers and run the one command it shows. It needs git, tmux and at least one agent program you are signed in to (Claude Code, Codex, OMP, OpenCode or Pi).
  2. Add a profile. On Profiles, pick one from the starter library or make your own. A profile says which agent program a helper uses, what it may do, and what it should know. Keep one that only reads and reports, and one that writes code.
  3. Add a project. On Projects, either let Handloom hold the project (it keeps the repository itself), or attach one you already have on GitHub or another host. Then have your computer fetch its own copy.
  4. Add the checks. On the same page, Add checks prepares a ./check that tests, lints and guards the project. It shows you the files first, and nothing changes until you press Put on the main branch. Without checks, Handloom can still run the work, but it has nothing objective to say about the result.
  5. Ask for something small. On Jobs, use Just ask: a sentence, a project, and Start. Watch the helper work, read the result, accept or send back.
  6. Finish. When the work is what you wanted, merge it into the project. Until you do, the project itself is untouched.

The parts, in plain words

HubThis web page and the system behind it. It keeps the list of jobs, who did what, the results and the people. It does not run helpers itself.
ComputerA machine you connected. A small program on it (the link) starts helpers, keeps their copies of the project, and runs the checks. Your code is worked on there, not on the hub.
ProjectA code repository. Each computer keeps its own copy. Held by Handloom, or attached from elsewhere.
ProfileA recipe for a helper: which agent program, what it may touch, what it was told. A new version is made each time you change it.
HelperA running agent made from a profile, in a terminal on a computer. You can watch its screen on its task.
Job and taskA job is something you asked for. It is split into tasks, each one done by one helper in its own copy. With Just ask and no lead, the job is one task for one helper.
LeadA helper that plans a bigger job, hands out tasks and reviews them. You can ask for one when a job has several steps.
ChecksA ./check in the project. Handloom runs it on a task's result and on the merge. Its answer comes from the machine, not from the helper's own claim.
InboxEverything waiting for you: results to look at, questions from helpers, work that stopped.

Working with it every day

Pick how much planning you want

  • One clear change: Just ask. One helper, no lead. Fastest, good for small and well-described work.
  • Bigger or vague: tick Have a lead plan it, and Show me the steps first so you approve the plan before anything runs.
  • Work that must meet a written definition of done: use the project kit's tasks. Write a spec with its risks, have a different helper draft failing tests (handloom job draft-tests), read them, keep the ones you want, then seal the task.

Reading a result

  • Open the job. Each task shows what changed (files, lines added and removed, the full diff), the check result, and the helper's note.
  • A green check means the project's own tests and rules passed. It does not mean the work is the right work: read the diff.
  • Use this result accepts it. Send back returns it with your note; after three send-backs the task stops and asks you what to do. Try again with another profile hands it to a different kind of helper. Stop this task ends it.
  • A finished task says who accepted it.

When something stops

Look in the Inbox first. It says in words what is waiting and what the options are. A helper that is stuck can be watched live from its task; a computer that went quiet shows on Computers.

Tips

  • Start small. Your first ask should be a change you could review in two minutes.
  • Say what not to do. "Change only the footer; leave the navigation alone" gives a smaller diff and a faster review.
  • Describe done, not steps. "Every page shows the year in its footer" beats a list of edits.
  • Don't trust a helper to state facts. Ask it to use what is in the project, and read for anything it invented.
  • Use a different helper to write tests than to build. The one who writes the code should not also decide what counts as done.
  • Keep checks honest. If a stage in factory.toml is empty (for example acceptance), it is skipped. Fill it in when you have tests for it.
  • Update the checks now and then. When Projects shows an update, Prepare an update brings the project's copy of the kit to the current one, with the same look-first step.
  • Nothing reaches the main branch without you. If a result looks wrong, you lose nothing by saying no.

Questions

Does a helper change my project directly?

No. It works in its own copy on a computer. Its result is shown to you, and only a person merges it into the project.

Where does my code live?

Held projects: in a repository on the hub. Attached projects: on your git host. In both cases each computer keeps its own copy, and helpers work there. The hub stores results, not your whole working tree.

The helper says it is done, but I don't trust it.

You shouldn't have to. Look at the check result, which Handloom's computer ran, and at the diff. Neither comes from the helper's own report.

The check failed. What now?

Open the task: it lists which stage failed and why. Send back with that reason, or try another profile. A check that says "the project's own checks are broken" is a problem in the project, not in the helper: fix that first.

A task says "blocked: a person decides".

The check reached something only a person may settle (for example a change to a protected file). Read the helper's note, decide, and either accept, send back with instructions, or change the project yourself.

Nothing happens after I press Start.

Look at the job's status line. "Starting the helper" can take a minute while the computer starts it. If the computer shows as offline on Computers, the link on it is not running. If a helper is waiting for a model that is rate-limited, try again with another profile.

When do I need a lead?

When the work has several parts that depend on each other, or you want a plan before work begins. For one clear change, skip it.

What is "Add checks" and do I have to?

It gives the project a standard ./check and rules about what a helper may change. You don't have to, but without it Handloom can only show the diff. It always shows you the files first and changes nothing until you confirm.

Who can do what?

Owners manage people, computers, profiles and settings. Anyone who can manage projects can add a project or its checks. Accepting work and merging it are for a person, never a helper. Viewers can look but not act.

Can I use it from the command line or an AI app?

Yes. Everything on these pages is also a handloom command. See Connect an AI app for using it from Claude or another app.

How do I undo something?

Before merging: stop the task, or just don't use it. After merging: it is an ordinary commit in your project, so revert it the way you would any other. Deleting projects, helpers or jobs from the hub is not possible yet.
