New job

Describe the work in plain words. A lead agent plans it, starts workers on your machine, and brings you the result to review. You only fill in what you know; everything else has a sensible default.

{{with .Extra}}

1. What should be done?

The title is what you will see in lists. The brief is what the agents read.

A good brief: the goal in a sentence; how you will know it is done (a command that passes, a file that exists); what not to touch. Short is fine.

2. Where does the work live?

Pick the machine that holds the files. For work that is not code (research, writing), leave the folder empty.

{{if not .Devices}}

A machine has to join first: Machines.

{{end}} {{if .Repos}}{{range .Repos}}{{end}}

The full path of a git repository (it starts with /). To find it, run pwd in the project folder on that machine. Each agent works in its own copy, so your files are never touched; accepted work is collected on a branch called job/<number>/integration for you to merge.

3. How will we know it worked?

A command that exits cleanly when the work is right. The machine runs it on every submission, and a lead cannot accept work that fails it.

Examples:

Without one, the lead judges by what the agents show as evidence, and you review the result.

4. Who leads it?

The lead plans the tasks, starts the workers and reviews their work. It never closes the job: you do.

{{if not .Profiles}}

The lead is started from a profile. Add one from the starter library (the Lead or Engineering lead starter).

{{end}}

The lead starts its workers from your other profiles, so make sure you have a worker profile too (for code, the Coder starter).

More options

Normally agents start from the project's latest commit. Name a branch to build on unmerged work, such as the integration branch of an earlier job.

A git repository of notes about the client, on the same machine. Every agent reads it first; what they learn is proposed on a branch you review and merge.
